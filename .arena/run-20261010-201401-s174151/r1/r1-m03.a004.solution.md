# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Аудит проведён по рабочему дереву ветки `backup-2026-10-10` как есть (есть незакоммиченные изменения, см. пробу П11). Проект не менялся: только чтение кода и безопасные GET-запросы к `http://localhost:3100` и `http://127.0.0.1:8081`. Записей в БД не было (ни одного INSERT/UPDATE/DELETE), пакеты не ставились, процессы не трогались. Секреты не приводятся. Отчёт на русском.

## 0. Ограничения и допущения

Жёсткие ограничения, в которых велось исследование (от самого сжимающего — дальше):

1. **Проект не менять** — только чтение и GET-пробы; фиксы ниже описаны, не применены.
2. **Пробы только безопасными GET** к dev-серверу и phpMyAdmin; без флуда, без перебора, без попыток обхода логина.
3. **Только SELECT к БД** — фактически к БД напрямую не подключались вовсе (хватило кода + HTTP-проб), права mysql-пользователя вживую не проверялись (отмечено как непроверенное, находка Л-7).
4. **Секреты не печатать** — пароли из `db/README.md` / `.env.local` не цитируются.
5. **Прод — статический экспорт** (`output: export` при `STATIC_EXPORT=1`, `next.config.js:6-7`) на GitHub Pages; dev на `:3100` — другой режим. Где поведение различается (заголовки, 404), это оговорено отдельно.
6. Допущения: dev-сервер на `:3100` соответствует рабочему дереву; `NEXT_PUBLIC_YM_ID` локально не задан (подтверждено отсутствием `mc.yandex` в HTML главной, проба П10).

## 3. Находки, ranked (новое)

### С-1. HIGH — Уязвимый Next.js 14.2.5 (известные CVE, обновление назрело)
- **Место:** `package.json:12` (`"next": "14.2.5"`).
- **Проверка:** инспекция + открытые базы (NVD/GitHub Advisories). По открытым данным ветка 14.2.5 затронута как минимум: **CVE-2025-29927** (обход middleware-авторизации через заголовок `x-middleware-subrequest`, CVSS 9.1, исправлено в 14.2.25/15.2.3) и **CVE-2024-39328** (cache-poisoning DoS, исправлено в 14.2.8).
- **Факт:** фреймворк старше security-фиксов на ~год; в проекте нет middleware (эксплуатация CVE-2025-29927 здесь напрямую не видна) и прод — статика, поэтому не CRITICAL, но dev-сервер и любые будущие API/middleware унаследуют дыру.
- **Фикс (без применения):** поднять `next` минимум до `14.2.25` (или актуальный 14.x/15.x после `tsc`+регресса), зафиксировать lock-файл, включить `npm audit` в чек-лист перед каждым деплоем.

### С-2. HIGH — Реальные пароли БД в отслеживаемом git-файле
- **Место:** `db/README.md` (в `git ls-files` — П11; `.gitignore` его не покрывает).
- **Проверка:** файл прочитан локально (секреты не цитируются): содержит логин/пароль root и логин/пароль пользователя `hkoop` + команды заливки дампа.
- **Факт:** секрет в системе контроля версий = компрометация при любом расшаривании/утечке репозитория; смена пароля без чистки истории не поможет.
- **Фикс:** (1) сменить оба пароля в MariaDB; (2) вычистить из истории (`git filter-repo`/`BFG`) и форс-пуш во все клоны; (3) держать доступы только в менеджере паролей + `.env.local`; (4) добавить в `.gitignore` `db/README.md` или вынести доступы в шаблон.

### Ю-1. HIGH — Яндекс.Метрика по коду грузится без согласия (152-ФЗ, cookie)
- **Место:** `app/layout.tsx:15,27-31` (рендер `ym(...)` при любом заданном `NEXT_PUBLIC_YM_ID`) + `components/CookieBanner.tsx:1-27` (никак не связан с загрузкой Метрики).
- **Проверка:** инспекция: условие — только наличие env, флага согласия никто не читает; баннер лишь пишет согласие и прячется. Локально счётчик выключен (в HTML нет `mc.yandex` — П10), нарушение латентное и выстрелит при включении счётчика (в `.env.example` он заготовлен).
- **Факт:** включение Метрики по этой схеме = передача cookie/IP третьей стороне до согласия. По позиции РКН cookie/аналитика — обработка ПДн: нужно предварительное согласие (ч. 1 ст. 6, ст. 9 152-ФЗ) и политика (ст. 18.1 152-ФЗ).
- **Фикс:** грузить `tag.js` и вызывать `ym(init)` только после согласия; до согласия — никакого `noscript`-пикселя тоже; в баннере кнопки «Принять»/«Отклонить» и ссылка прямо на `/docs/politika.pdf`; решение хранить со сроком и возможностью отзыва из футера.

### С-3. HIGH — Нет заголовков безопасности; фикс — только средствами статического хостинга
- **Место:** HTTP-ответы dev-сервера (все страницы) — проба П1; прод-режим `output: export` — `next.config.js:6-7`.
- **Проверка:** `curl -I /` — отсутствуют `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`; `Strict-Transport-Security` отсутствует.
- **Факт:** сайт можно встроить в чужой `iframe` (кликджекинг формы/баннера), нет защиты от MIME-sniffing, нет CSP-рамок для инлайновых скриптов (`layout.tsx:19,29`), referrer не ограничен. Уточнение про прод: `headers()`/`redirects()` из `next.config.js` при `output: export` игнорируются — их Next-сервер не отдаёт, отдаёт GitHub Pages; у `X-Frame-Options` нет meta-эквивалента, `frame-ancestors` в `<meta http-equiv="Content-Security-Policy">` браузерами игнорируется, GitHub Pages кастомные заголовки не поддерживает.
- **Фикс:** (1) до смены хостинга: `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; img-src 'self' data: https:; script-src 'self' https://mc.yandex.ru; style-src 'self' 'unsafe-inline'; frame-src https://yandex.ru; object-src 'none'; base-uri 'self'">` (без `frame-ancestors` — он там не работает), `referrerpolicy`/`referrer` meta `strict-origin-when-cross-origin`, JS-защита от фрейминга (frame-busting) как временная мера, `rel="noopener noreferrer nofollow"` наружу, убрать инлайн-скрипты в отдельные файлы; (2) по-настоящему: вынести прод за CDN, умеющий заголовки (Cloudflare Pages/Netlify `_headers`/Nginx), и там задать `Content-Security-Policy` (с `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, на прод-домене `HSTS`; после деплоя проверить `curl -I` прод-URL.

### С-4. MEDIUM — Два сырых `<img src>` из БД мимо `safeHref`: фото книги почёта и логотипы партнёров
- **Место:** (а) `app/honor/page.tsx:14` (`<img src={h.photo} ...>` напрямую из БД); (б) `components/PartnersStrip.tsx:11` (`<img src={p.logo} ...>` напрямую из БД, при том что `p.url` строкой ниже в `:21` идёт через `safeHref`).
- **Проверка:** инспекция + П10 (текущие значения безобидны: site-relative пути). Атака — только при контроле БД (через phpMyAdmin/дамп): запись вида `https://evil/...` даст хотлинк/трекер, `data:`-схема в `img` отрендерится (современные браузеры `javascript:` в `img` не исполняют, но `data:image/svg+xml` и внешний трекинг реальны); `onError`-ветка ошибку скрывает, но URL всё равно запрашивается.
- **Фикс:** оба места — `const src = safeHref(...) ?? null`, при `null` — плейсхолдер (у почёта ветка уже есть; у партнёров — текстовая заглушка с именем); в идеале ограничить `src` паттернами `/images/...` + явным allowlist CDN; `alt` оставить (React экранирует текстом).

### С-6. MEDIUM — iframe-превью PDF без `sandbox` и без ограничения домена
- **Место:** `components/DocsFilter.tsx:42` (`setPreview(safeHref(d.file_local)!)`) + `components/DocsFilter.tsx:50-56` (`<iframe src={preview} width="100%" height="600" title="PDF">` без `sandbox`/`referrerpolicy`).
- **Проверка:** инспекция: `safeHref` (`lib/url.ts:3-9`) режет только схему — любой `https://` проходит, включая `https://evil.example/phish.html`; iframe открывается внутри оформления сайта под заголовком «Просмотр PDF».
- **Факт:** при контроле поля `file_local` в БД произвольная внешняя страница рендерится во фрейме доверенного сайта (фишинг/трекер от имени профсоюзов); без `sandbox` внешняя страница получает больше возможностей, чем нужно для PDF.
- **Фикс:** превью — только для site-relative `/docs/*.pdf` (строгое условие, не общий `safeHref`); внешние URL — не во фрейм, а ссылкой в новой вкладке с `rel="noopener noreferrer nofollow"`; фрейму добавить `sandbox=""` (пустой, разрешить минимум при нужде) + `referrerpolicy="no-referrer"` + `loading="lazy"`; заголовок «Просмотр PDF» показывать только для локальных PDF.

### С-5. MEDIUM — `safeHref` разрешает любой http(s)-домен: компрометация строки БД = фишинговая ссылка
- **Место:** `lib/url.ts:3-9` (регулярка `^(https?:\/\/|\/[^/\\])`), потребители: `PartnersStrip`, `DocsFilter`, `contacts/page.tsx`, `app/page.tsx:37` (первые две ветки).
- **Проверка:** инспекция: `https://anything` проходит; `rel="noreferrer"` без `noopener`/`nofollow` (`PartnersStrip.tsx:29`, `page.tsx:95`, `DocsFilter.tsx:43`); соцсети в контактах полностью из БД.
- **Факт:** при контроле БД любой партнёр/документ/соцсеть превращается в ссылку на злоумышленника с доверием профсоюзного сайта; `noreferrer` в современных браузерах подразумевает `noopener`, но явного `nofollow`/`noopener` нет.
- **Фикс:** allowlist внешних доменов по явному списку + `rel="noopener noreferrer nofollow"` везде наружу; смену соцсетей/партнёров подтверждать вторым лицом (регламент пресс-службы).

### С-7. MEDIUM — Фолбэк `docHref` через `old_url` без `safeHref`
- **Место:** `app/page.tsx:37`: `safeHref(d.file_local) || safeHref(d.file_old) || (typeof d.old_url === "string" && d.old_url.startsWith("/") ? "https://habprof.ru"+d.old_url : "/docs")`.
- **Проверка:** инспекция: третья ветка проверяет только ведущий `/` и конкатенирует с внешним хостом `habprof.ru` вне контроля; через `safeHref` не прогоняется. Примеры: `old_url="/\\evil"`, строки с пробелами/управляющими символами, `"/%0d%0a..."` дают битую или неожиданную ссылку `https://habprof.ru/...`; ветка же переключает `target/rel` (`page.tsx:95`: `target={d.file_local ? undefined : "_blank"}`).
- **Факт:** та же граница «строка из БД → href», что С-5, но с более слабой валидацией и внешним хостом.
- **Фикс:** прогнать итог через `safeHref` и отклонить при `null` (фолбэк `/docs`); дополнительно разрешить только символы `[-a-zA-Z0-9_/.%]`, отрезать управляющие символы, проверить что после `https://habprof.ru` идёт ровно один `/` и нет `//`/`\\`; внешние ссылки — с `rel="noopener noreferrer nofollow"`.

### Ю-2. MEDIUM — Cookie-баннер не дотягивает до согласия по 152-ФЗ
- **Место:** `components/CookieBanner.tsx:12-25`.
