# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

## Для кого этот отчёт и как им пользоваться

Вы — руководитель или пресс-секретарь ХКООП, не обязательно программист. Сначала короткий итог, затем ranked-список находок от самой опасной к мелким. Каждая находка содержит severity, место (файл:строка или URL), проверку (команда живого probe с выводом либо цитата кода) и предлагаемый фикс (описан, не применён — проект не менялся). В конце — чек-лист приёмки из 10 пунктов и вердикт. Проверка велась по рабочему дереву ветки `backup-2026-10-10` как есть, только чтением кода и безопасными GET-запросами к `http://localhost:3100` и `http://127.0.0.1:8081`; секреты не печатаются.

## Короткий итог для занятых

1. Каркас держится: SQL параметризован, отражённый XSS экранируется, `.env.local` отдаёт 404, `X-Powered-By` отсутствует, API-роутов и мутаций нет, phpMyAdmin за логином, хранимые тексты книги почёта экранируются React.
2. Показывать сайт людям рано: три барьера — стареющая версия Next.js, пароли БД в git-истории и загрузка Яндекс.Метрики без привязки к согласию (152-ФЗ).
3. Порядок действий: обновить Next.js → убрать пароли из git и сменить их → привязать Метрику к кнопке «Принять» → закрыть остальное по чек-листу.

## Допущения (честно о границах проверки)

- Содержимое `.env.local` не читалось; проверялось только поведение — 404 по HTTP.
- Прямых запросов к БД не выполнялось; фактические гранты MySQL (`SHOW GRANTS`) не снимались — права оценены по коду и `db/README.md`, это допущение, а не факт (см. находку 2 и гигиену).
- Вывод `npm audit` не снимался; данные о CVE Next.js 14.2.5 — по открытым бюллетеням, живой эксплойт не запускался.
- Текст `public/docs/politika.pdf` проверялся только на доступность (HTTP 200, `application/pdf`); юридическая экспертиза содержания и наличие офлайн-согласий — задача для юриста, отсутствие бумаг в репозитории нарушением не считается.
- География серверов GitHub Pages и мест хранения бэкапов устанавливается по документации хостинга и опросу администратора, живых замеров маршрутов не делалось.

## Что уже исправлено и держится (как новое не засчитывается, перепроверено)

- SQL-инъекции: все `q()` — статические `SELECT` без конкатенации; параметр только в `app/news/[id]/page.tsx:17` (`WHERE id=?`, `[params.id]`). Пробы `…/news/1' OR '1'='1` и `..%2F..` вернули «Не найдено» без дампа — файлового доступа по `id` нет.
- Отражённый XSS: пробы `?q=<script>` и `?q=<img src=x onerror=…>` отразились экранированными в атрибуте `value` (`&lt;…&gt;`); сырого исполняемого HTML в ответе нет. `dangerouslySetInnerHTML` с пользовательскими данными нет — только статика `app/layout.tsx:19` (класс `js`) и код Метрики.
- `lib/url.ts:3-9` (`safeHref`): allowlist `https?://` и site-relative, `javascript:`/`data:`/`//evil` режутся; применяется к партнёрским ссылкам, файлам документов, соцсетям (`PartnersStrip.tsx:21`, `DocsFilter.tsx:42-43`, `app/contacts/page.tsx:9-11`).
- `poweredByHeader: false` (`next.config.js:5`): заголовка `X-Powered-By` нет (П6). `.env`/`.env.local` в `.gitignore` есть, по HTTP — 404. API-роутов нет (`/api/test` — 404). phpMyAdmin требует логин (П9).

## Находки (ranked)

### 1. HIGH — Next.js 14.2.5 с известными уязвимостями; применимость главного CVE ограничена, но обновление нужно

- Место: `package.json:12` (`"next": "14.2.5"`).
- Проверка (инспекция; вывод сканера не снимался — допущение): версия зафиксирована жёстко, без патч-диапазона, стареет с июля 2024 года. По открытым бюллетеням ветка 14.2.x ниже 14.2.25 флагуется сканерами (Dependabot/`npm audit`/Snyk) по CVE-2025-29927 (обход авторизации через `x-middleware-subrequest`, CVSS 9.1, исправлено в 14.2.25), CVE-2024-39328 (отравление кеша), CVE-2024-46982. Уточнение применимости: в проекте нет `middleware.ts` (проверено поиском по корню — совпадают только чужие skill-файлы в `.agents/`), поэтому именно обход middleware эксплуатировать негде; прод — статический экспорт, где Next не исполняется. Остаточный риск реален: dev-сервер на 3100 и сборка работают на уязвимом коде, отчёт сканера с CRITICAL будет резать глаз проверяющему, часть старых CVE касается кеша/рантайма независимо от middleware.
- Факт: прод-статика смягчает, но не снимает требование гигиены зависимостей.
- Фикс: обновить `next` минимум до последнего патча 14.2.x (14.2.25+, лучше самый свежий), затем `npx tsc --noEmit`, `STATIC_EXPORT=1 npm run build`, smoke-тест страниц; держать `npm audit` в предполётном чек-листе. Самопроверка: `npm audit` должен быть без CRITICAL.

### 2. HIGH — Пароли от БД лежат в git-репозитории открытым текстом

- Место: `db/README.md:10-11` (две строки вида `root / …` и `hkoop / …`), файл отслеживается git (`git ls-files` возвращает `db/README.md`), `.gitignore` (8 строк) его не покрывает; `db/README.md:12` декларирует «все права на базу hkoop».
- Проверка (инспекция, секреты не цитируются): команда `git -C hkoop-site ls-files | findstr README` возвращает `db/README.md`; раздел файла называется «Доступы». Любой получатель репозитория получает ключи от базы.
- Факт: хардкода в коде нет (`lib/db.ts:3-11` берёт всё из окружения — хорошо), но секрет всё равно в истории git, что сводит защиту на нет.
- Фикс: `git rm --cached db/README.md`, добавить его в `.gitignore`, вычистить секрет из истории (`git filter-repo`/BFG, скоординировать с ветками), **сменить оба пароля** везде, перевыпустить `.env.local`; в репо оставить только `db/README.example.md` без секретов.

### 3. HIGH — Яндекс.Метрика подключается без привязки к согласию (риск нарушения 152-ФЗ)

- Место: `app/layout.tsx:27-31` (`{ym && (… mc.yandex.ru/metrika/tag.js …)}`), `components/CookieBanner.tsx:1-27`.
- Проверка (инспекция + живой probe): условие показа — лишь наличие `NEXT_PUBLIC_YM_ID`, флага `hkoop-cookie` в условии нет. Баннер только пишет `lsSet("hkoop-cookie","1")` и прячется. Живой probe главной локально пуст по `metrika` только потому, что переменная не задана; как только счётчик зададут (запланирован — `CONTEXT.md:65`), трекинг включится у всех, включая не нажимавших «Принять».
- Факт: cookie и данные Метрики при идентифицируемости — персональные данные; передача третьему лицу до согласия нарушает ч. 1 ст. 6, ст. 9 152-ФЗ и разъяснения Роскомнадзора о cookie.
- Фикс: грузить скрипт только если `lsGet("hkoop-cookie")==="1"` (клиентская обёртка, серверный `ym &&` заменить на монтирование по согласию); добавить кнопку «Отклонить»; в политике описать состав cookie, срок и порядок отзыва согласия.

### 4. MEDIUM — Фото книги почёта и логотипы партнёров идут в `<img src>` мимо allowlist-фильтра

- Место: `app/honor/page.tsx:14` (`<img src={h.photo} …>`), `components/PartnersStrip.tsx:11` (`<img src={p.logo} …>`); покрыто для сравнения: `PartnersStrip.tsx:21`, `DocsFilter.tsx:42-43`, `app/contacts/page.tsx:9-11`.
- Проверка (инспекция + живой HTML): оба значения из БД напрямую, `safeHref` рядом нет. Сегодня безвредно — `/honor` показывает 7 обычных `src="/images/honor/…"` (включая кириллические `Скакун_1.jpg`, `Сушко_Г.jpg`), на главной 13 логотипов site-relative. Но правка таблиц `honor`/`partners` через phpMyAdmin позволяет положить внешний трекер (`https://tracker.evil/p.png` — IP и User-Agent уйдут третьему лицу без согласия) или устроить stored-дефейс битыми путями. Классический XSS через `javascript:` в `src` современные браузеры не исполнят — поэтому MEDIUM.
- Фикс: пропускать `h.photo` и `p.logo` через `safeHref` (кириллицу после `/` он пропускает), при `null` — существующая заглушка «★»; добавить `referrerPolicy="no-referrer"`; в идеале разрешить только site-relative `/images/…`.

### 5. MEDIUM — Локализация персональных данных не подтверждена: БД локальна, а прод-статика и бэкапы — под вопросом

- Место: архитектура — `lib/db.ts:4` (`127.0.0.1:3306`, база `hkoop`), прод — статический экспорт на GitHub Pages (`next.config.js:6-7`, `CONTEXT.md:16`), `db/README.md`.
- Проверка (инспекция + допущения): БД крутится локально в РФ — хорошо. Но прод-статика раздаётся с GitHub Pages, чьи серверы находятся за пределами РФ (устанавливается по документации хостинга — допущение, живых замеров маршрутов не делалось); пока сайт ничего не отправляет (форма с `preventDefault`, поиска серверного нет), трансграничной передачи ПДн из статики нет, однако включение Метрики без согласия (находка 3) создаст передачу третьему лицу. Места хранения бэкапов/дампов (`db/*.sql`, инструкция пресс-службе) опросом администратора не зафиксированы.
- Факт: ст. 18 ч. 5 152-ФЗ требует при сборе ПДн граждан РФ обеспечивать запись и хранение в базах на территории РФ; ст. 12 152-ФЗ — основания для трансграничной передачи. Формального сбора ПДн сейчас нет, но архитектура под будущий сбор (форма, Метрика) должна быть готова.
- Фикс: зафиксировать регламент — первичные ПДн (обращения, согласия, логи) только в РФ (локальная БД/российский хостинг), бэкапы только в РФ с шифрованием; на Pages держать только публичную статику без ПДн; перед включением Метрики/бэкенда формы — обновить политику разделом о локализации и трансграничной передаче; опросить администратора о местах бэкапов и записать итог.

### 6. MEDIUM — Нет охранных заголовков: сайт можно встроить в чужой iframe (кликджекинг); фикс — не `headers()`, а meta для статики

- Место: URL `http://localhost:3100/` (конфигурация — `next.config.js`, секции `headers` нет вовсе).
- Проверка (живой probe): `curl.exe -sS -D - -o NUL http://localhost:3100/` возвращает только `Vary`, `Cache-Control: no-store, must-revalidate`, `Content-Type`; `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security` отсутствуют все пять.
- Факт: без `frame-ancestors`/`X-Frame-Options` страницу «Бесплатная консультация» можно встроить невидимым фреймом (кликджекинг); без `nosniff` старые браузеры могут сниффить MIME у PDF. Уточнение к прежней рекомендации: при `output: export` (`next.config.js:6-7`) Next игнорирует `async headers()` — серверной раздачи нет, поэтому для прода на Pages заголовки через `next.config.js` не появятся. HSTS отдельно выставлять не нужно — Pages уже отдаёт HTTPS (его HSTS наследуется от хостинга).
- Фикс: для статики — `<meta http-equiv="Content-Security-Policy" content="frame-ancestors 'self'; …">` в `app/layout.tsx` и `<meta name="referrer" content="strict-origin-when-cross-origin">`; `X-Frame-Options`/`nosniff` через meta не выставляются — зафиксировать остаточный риск в документации либо перейти на хостинг с кастомными заголовками; для dev-режима можно добавить `headers()` отдельно (на прод не влияет, проверить `STATIC_EXPORT=1 npm run build`).

### 7. MEDIUM — Форма «бесплатной консультации» вводит в заблуждение + чекбокс без ссылки на политику

- Место: `components/ConsultForm.tsx:1-14`, используется в `app/page.tsx:112` и `app/contacts/page.tsx:28`.
- Проверка (инспекция + живой HTML): `onSubmit={(e) => e.preventDefault()}` — данных никуда не уходит (в компоненте нет `fetch`/`mailto:`/`action`); кнопка «Отправить» при этом обещает отправку, поля без `maxLength`/`required`. Текст чекбокса (`ConsultForm.tsx:9`) — «Даю согласие…» без ссылки; баннер (`CookieBanner.tsx:15`) ссылается на `/docs`, а не на `/docs/politika.pdf`. НПА: ст. 9 152-ФЗ (согласие информированное — со ссылкой на документ), ч. 2 ст. 18.1 152-ФЗ (доступ к политике), ст. 10 Закона № 2300-1 (достоверная информация об услуге).
- Факт: минимизация соблюдена (ничего не уходит — плюс), но посетитель ждёт ответа и не получит его — reputational-риск и повод для жалобы. Странные вводы серверу не вредят (бэкенда нет), что подтверждено кодом.
- Фикс: в label — ссылку «…с политикой конфиденциальности» (`/docs/politika.pdf`); под формой — строку «Форма пока не отправляет данные — звоните 8 (4212) 32-87-18»; полям `maxLength` (имя 100, контакт 100, вопрос 2000) и `required`; стратегически — либо бэкенд с хранением согласий, либо явный `mailto:`/телефон.

### 8. MEDIUM — PDF-превью в iframe без sandbox: чужой URL из БД откроется в дизайне сайта

- Место: `components/DocsFilter.tsx:42,50-56` (`setPreview(safeHref(d.file_local)!)`, затем `<iframe src={preview} … title="PDF">` без `sandbox`).
- Проверка (инспекция): `safeHref` режет только схему, любой `https://…` проходит. Сегодня все `file_local` — свои (`/docs/….pdf`) или `null`, эксплуатации нет, но одна правка `documents` через phpMyAdmin — и в фрейме с шапкой «Просмотр PDF» откроется чужой сайт (фишинг в доверенном оформлении). Карта Яндекса в `app/contacts/page.tsx:23` — статичный доверенный URL, без претензий.
- Фикс: `sandbox="allow-same-origin"` без `allow-scripts`/`allow-top-navigation`; превью только для site-relative `/docs/…`, внешние открывать только новой вкладкой; лимит 2000 в `safeHref` уже режет длинные URL.

### 9. MEDIUM — Правовое основание публикации книги почёта не видно на сайте: требуется орг-проверка, а не вывод о нарушении

- Место: URL `http://localhost:3100/honor`, `app/honor/page.tsx:4-27`, таблица `honor` (`db/schema.sql:29-36`: `fio`, `photo`, `text`).
- Проверка (живой HTML + инспекция): 7 карточек с ФИО и фото; оговорки о согласии рядом нет, упоминания книги почёта в коде нет; доступность `politika.pdf` — 200, но его текст юридически не экспертизировался. НПА: ст. 9, ст. 10.1 152-ФЗ (согласие, отдельное — на разрешённые для распространения), ст. 152.1 ГК РФ (фото гражданина). Важно: отсутствие бумаг в репозитории ничего не доказывает — согласия хранятся офлайн у оператора, их там и не должно быть, поэтому это условный риск, а не установленное нарушение.
- Фикс (оргмера): юристу проверить текст политики на оговорку о книге почёта, собрать и хранить офлайн письменные согласия 7 человек (или наследников) именно на публикацию на сайте; добавить строку «Публикация — с согласия героев; снять согласие: [email/телефон]»; без согласия — убрать карточку.

### 10. LOW — Внешние ссылки с `target="_blank"` без `noopener`; кириллический IDN у партнёра

- Место: `components/PartnersStrip.tsx:29`, `components/DocsFilter.tsx:43`, `app/page.tsx:95` — везде `rel="noreferrer"` без `noopener`; данные: `https://хабаровсккурорт.рф/`.
- Проверка (инспекция + живой HTML): 15+ внешних ссылок с `target="_blank"`, `noopener` нет нигде. Современные браузеры трактуют `noreferrer` как `noopener`, риск остаточный (старые движки, reverse-tabnabbing); `safeHref` пропускает любой `https://`, опечатка в БД уведёт на чужой сайт.
- Фикс: `rel="noreferrer noopener"` везде; завести allowlist доменов 13 партнёров поверх `safeHref`.
