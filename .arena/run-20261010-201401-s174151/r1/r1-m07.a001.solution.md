# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Дата: 10.10.2026. Объект: `hkoop-site`, ветка `backup-2026-10-10` (рабочее дерево как есть). Стек: Next.js 14.2.5 + React 18 + TS, mysql2, MariaDB `hkoop` на 127.0.0.1:3306, dev http://localhost:3100, phpMyAdmin http://127.0.0.1:8081, прод — статический экспорт (`output: export`) на GitHub Pages. Проект не менялся: только чтение кода и безопасные GET-пробы. Секреты не печатаются (проверялись только имена ключей и факты наличия).

## Открытые вопросы и принятые допущения

1. Прод = статический экспорт: весь SQL выполняется только в момент сборки, в браузере пользователя SQL и секретов БД нет. Следствие: серверные заголовки через `next.config.js` в проде невозможны (см. F7).
2. БД доверенная: писать в неё может только аппарат через phpMyAdmin, поэтому внешние https-ссылки из БД — не уязвимость сами по себе, но поверхность для stored-XSS/трекинга проверена.
3. Проверены имена ключей `.env.local` (значения не читались и не печатаются).
4. Версии CVE для Next сверены с публичными бюллетенями; где точный номер не подтверждён, это оговорено.
5. Права mysql-пользователя живой БД не проверялись живым запросом (см. F13): вывод о правах строится только на декларации `db/README.md`, живой `SHOW GRANTS` должен выполнить владелец.
6. Критерий «ошибки» из задания (нет 500/стектрейсов) считается пройденным отдельно от SEO-гигиены кодов ответа (см. F9).

### F7. MEDIUM — Нет security-заголовков; `headers()` в next.config.js для прод-статики неприменим

- Место: `next.config.js` (нет секции `headers`), живой ответ dev-сервера.
- Проверка (живая + инспекция): `curl -s -D - http://localhost:3100/ -o NUL` → только `Vary / Cache-Control: no-store / Content-Type`; `X-Powered-By` отсутствует (держится, `poweredByHeader:false`), но `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security` — ни одного. Инспекция `next.config.js:2,6-25`: прод — `output: export` при `STATIC_EXPORT=1`, редиректы уже условно отключены при `isExport` — тот же механизм означает, что и секция `headers()` в статическом экспорте не эмитится в прод. То есть совет «добавить headers()» сам по себе прод на GitHub Pages не закроет.
- Факт: сайт можно встроить в чужой iframe (кликджекинг формы/баннера), нет защиты от MIME-sniffing и утечек referrer на внешние PDF/соцсети.
- Фикс: честно разделить: а) для GitHub Pages (текущий прод) серверных заголовков нет — применять только экспортируемые компенсации: `<meta name="referrer" content="strict-origin-when-cross-origin">`, `<meta http-equiv="X-Content-Type-Options" content="nosniff">` (ограниченно), JS frame-busting для страниц с формой, фасад для Яндекс-iframe (см. F4), внешних `img` без согласия не грузить; б) секцию `headers()` в `next.config.js` добавлять только при переезде на Node-хостинг (frame-ancestors 'self', nosniff, строгий referrer, Permissions-Policy без камеры/микрофона/гео); HSTS — только когда появится свой домен с HTTPS.

## Что проверено и держится (уже исправленное — как новое не засчитывается; плюс разжалованные пункты)
