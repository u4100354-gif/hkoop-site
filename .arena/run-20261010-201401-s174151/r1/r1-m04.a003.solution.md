# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Аудит проведён по рабочему дереву ветки `backup-2026-10-10` как есть, без изменений проекта, БД (только чтение), git, пакетов и процессов. Живые пробы — только безопасные `GET` к `http://localhost:3100` и `http://127.0.0.1:8081`. Секреты не печатаются. Проект не менялся.

## Допущения

1. Прод — статический экспорт (`output: export`) на GitHub Pages; серверного рантайма в проде нет, поэтому часть находок бьёт по dev-серверу, сборке и будущему SSR.
2. БД правит доверенный администратор через phpMyAdmin; модель угроз для хранимых данных — компрометация учётки/ошибка оператора, а не внешний злоумышленник с записью.
3. Тексты НПА цитируются по смыслу; точные статьи указаны у каждого юридического пункта.

## Проверено — держится (как новое не засчитывается)

- Все SQL-запросы параметризованы: все вызовы `q()` — это `SELECT` без конкатенации, единственный параметр — `WHERE id=?` (`app/news/[id]/page.tsx:17`).
- Живые пробы SQL-инъекции и путей: `GET /news/test' OR '1'='1` → `200`, страница «Не найдено», без ошибок и дампов; `/news/..%2f..%2fetc%2fpasswd`, `/news/<script>alert(1)</script>` → «Не найдено»/`404`, чтения файлов нет, полезная нагрузка в исполняемом HTML не отражена (видна только внутри JSON RSC-пейлоада `initialCanonicalUrl`, что не исполняется).
- Отражённый XSS через поиск отсутствует: `GET /search?q=<img src=x onerror=alert(1)>` → `200`, ввод отражён только в экранированном `value="&lt;img …&gt;"`. HeaderSearch (`components/HeaderSearch.tsx:44`) уходит через `encodeURIComponent`, результаты рендерит React-текстом; фильтры новостей/документов (`DocsFilter.tsx:20-23`) — клиентские, без вставки HTML; длинные строки (проверено вводом 2000+ символов) лишь дают «Ничего не найдено», без падений.
- Ошибки не светят детали: несуществующий id (`GET /news/nonexistent-id-12345` → `200` со страницей «Не найдено»), кривые параметры и `GET /robots.txt` → `404` штатной страницей Next (с `<meta name="robots" content="noindex"/>` по умолчанию), без стектрейсов.
- `lib/url.ts:3-8` (`safeHref`) закрывает `javascript:`/`data:`/`//evil` для всех `href` из БД и `iframe`-превью (`components/DocsFilter.tsx:42-43,56`, `components/PartnersStrip.tsx:21-29`, `app/contacts/page.tsx:9-11`).
- `poweredByHeader: false` (`next.config.js:5`) держится: в живых заголовках `GET /` заголовка `X-Powered-By` нет.
- `.env.local` по HTTP отдаёт `404` штатной страницей 404 без секретов; `GET /.git/HEAD` → тоже `404`.
- `.gitignore:1-8` покрывает `.env`, `.env.local`, `.next-export/`; хардкода пароля БД в коде нет (`lib/db.ts:3-11` — только переменные окружения).
- phpMyAdmin отвечает `200` страницей входа (закрыт логином — держится).
- API-роутов и мутаций нет: файлов `app/**/route.ts` и `middleware.*` нет, все формы клиентские (`ConsultForm` — только `preventDefault`, `components/ConsultForm.tsx:4`).
- Содержимое БД чистое на момент аудита: `SELECT`-проба таблиц `partners` (13), `honor` (7), `documents`, `site_settings` (11) — ни одного `javascript:`/`data:`/`onerror`/`<script>`; все `url`/`logo`/`photo` — `https://…` или site-relative `/images/…`.
- Импринт есть (не находка): адрес, телефон и email присутствуют в шапке (`components/Header.tsx:52-54`), футере (`components/Footer.tsx:7-10`) и на `/contacts` (`app/contacts/page.tsx:14-20`) — требования ст. 10 Федерального закона от 27.07.2006 № 149-ФЗ к контактам владельца сайта закрыты.
- Версия для слабовидящих есть и работает (не находка): кнопка «Версия для слабовидящих» в шапке (`components/Header.tsx:55-57`), `ViProvider` (`components/ViProvider.tsx:5-46`) переключает `vi-mode`, панель даёт крупный шрифт и отключение картинок; полное соответствие ГОСТ Р 52872-2019 требует отдельной экспертизы, но базовый механизм на месте.
- Партнёрские ссылки — информационные (не находка): `PartnersStrip` выводит названия организаций без рекламных формулировок и CTA; признаков рекламы по Федеральному закону от 13.03.2006 № 38-ФЗ (требующей маркировки/erid) не выявлено; при добавлении рекламных текстов понадобится пересмотр.
- Локализация и контакты оператора (не находка): трансграничной передачи нет (форма ничего не отправляет, трекер сегодня не грузится — см. ниже), контакты оператора на сайте есть; отдельного нарушения тут не констатируется.

## Находки (ранжированный список)

### CRITICAL-1. Уязвимый рантайм: `next 14.2.5` с известными CVE

- **Место:** `package.json:12` (`"next": "14.2.5"`).
- **Проверка (инспекция кода + сверка с бюллетенями):** зафиксирован пин `14.2.5` — версия старше крупных security-релизов ветки 14.2.x. Публичные CVE линейки: **CVE-2025-29927** (обход авторизации через заголовок `x-middleware-subrequest`, CVSS 9.1, исправлен в 14.2.25), **CVE-2024-46982 / CVE-2024-39332** (cache-poisoning/DoS, исправлены в 14.2.9+). Смягчает то, что `middleware.*` в проекте отсутствует и прод — статика, но dev-сервер (`localhost:3100`), сборка и любой будущий SSR/API используют уязвимый рантайм.
- **Факт:** зависимость с известными критическими уязвимостями в цепочке сборки и dev-окружении; любой сканер зависимостей провалит комплаенс.
- **Фикс (описать, не применять):** поднять `next` минимум до `14.2.25`, лучше до последнего патча ветки 14.2.x; прогнать `npm audit`, пересобрать статику, перепроверить живые пробы из этого отчёта.

### HIGH-1. Пароли БД лежат в git: `db/README.md` закоммичен и не покрыт `.gitignore`

- **Место:** `db/README.md:8-12`, `.gitignore:1-8`.
- **Проверка (инспекция + read-only git):** `git ls-files db/README.md` → файл отслеживается; `.gitignore` его не покрывает; внутри — пароли root и пользователя БД в открытом виде. `.env.local` при этом не отслеживается (корректно).
- **Факт:** секрет уже в истории репозитория — удаление файла из дерева его не уберёт; любой клон/форк/утечка токена раскрывает доступ к СУБД.
- **Фикс:** срочно сменить оба пароля; вычистить файл из истории (`git filter-repo`/`BFG`) с координацией всех клонов; переписать `db/README.md` на плейсхолдеры; добавить исключение в `.gitignore`; хранить доступы только локально.

### HIGH-2. Яндекс.Метрика включается мимо согласия: баннер согласию не gating'ит

- **Место:** `app/layout.tsx:15,27-31`, `components/CookieBanner.tsx:1-27`.
- **Проверка (инспекция кода + живой probe):** условие вставки Метрики — только `ym && …`, флаг `hkoop-cookie` из `localStorage` нигде не читается для этого решения; `noscript`-пиксель `https://mc.yandex.ru/watch/${ym}` — тоже безусловный. Живая проба главной сегодня не содержит `mc.yandex` (счётчик не задан — нарушения по факту нет), но достаточно задать `NEXT_PUBLIC_YM_ID`, и трекер с `clickmap:true,trackLinks:true` встанет у всех посетителей до клика «Принять».
- **Факт:** разрыв между текстом согласия и фактической загрузкой трекера; включение счётчика одной переменной окружения сразу включает слежку без согласия — вопреки тексту баннера. НПА: **ст. 9, 18, 18.1 Федерального закона от 27.07.2006 № 152-ФЗ** (обработка только с согласия субъекта, информирование, политика оператора); практика РКН по cookie-баннерам (отказ должен быть не сложнее согласия).
- **Фикс:** gating'ить вставку скрипта и пикселя Метрики флагом согласия (`hkoop-cookie === "1"`), читать его до вставки; добавить в баннер кнопку «Отклонить» равного веса; ссылку в баннере вести прямо на `/docs/politika.pdf`; Яндекс-карту на `/contacts` грузить лениво после согласия (клик-плейсхолдер).

### HIGH-3. Нет ни одного заголовка безопасности: кликджекинг и MIME-сниффинг (на Pages — только через meta)

- **Место:** `next.config.js:1-27` (нет секции `headers`), живой ответ сервера.
- **Проверка (живой probe):** `curl.exe -sSI http://localhost:3100/` → только `Vary`, `Cache-Control: no-store, must-revalidate`, `Content-Type`, `Date`, `Connection`. Отсутствуют: `Content-Security-Policy` (или `frame-ancestors`), `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security`.
- **Факт:** сайт можно встроить в чужой `iframe` (кликджекинг — в т.ч. вокруг формы консультации и cookie-баннера); браузеры без `X-Content-Type-Options` могут сниффить типы. Честная оговорка: на заявленном проде (GitHub Pages при `output: export`) кастомные HTTP-заголовки отдать нельзя — секция `headers` в `next.config.js` при экспорте игнорируется, а файл `_headers` там не поддерживается (это механизм Netlify/Cloudflare).
- **Фикс:** для Pages — `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; img-src 'self' data:; frame-src https://yandex.ru; script-src 'self' https://mc.yandex.ru">` и `<meta name="referrer" content="strict-origin-when-cross-origin">` в `app/layout.tsx`, плюс `sandbox`/`allow` по минимуму у `iframe` карты и PDF-превью; для настоящих заголовков (`frame-ancestors`, `nosniff`, `HSTS`) — переезд на хостинг с поддержкой заголовков либо прокси (Cloudflare) перед Pages.

### MEDIUM-1. Два `src` из БД идут мимо allowlist: фото книги почёта и логотипы партнёров

- **Место:** `app/honor/page.tsx:14` (`<img src={h.photo} …>`), `components/PartnersStrip.tsx:11` (`<img src={p.logo} …>`).
- **Проверка (инспекция кода + SELECT-проба):** все `href`/`iframe` из БД идут через `safeHref`, а эти два `src` — напрямую. Текущие данные чистые (все 13 логотипов и 7 фото — site-relative/`https`, подозрительных схем нет). React экранирует текст, поэтому классического stored-XSS сегодня нет, но при компрометации БД в `src` ляжет произвольное значение без барьера.
- **Факт:** неполное покрытие allowlist — единственный класс выводов из БД без фильтра.
- **Фикс:** пропускать `h.photo` и `p.logo` через `safeHref` (с запасной заглушкой как сейчас через `onError`), унифицировать с остальными выводами.

### MEDIUM-2. Форма консультации молча выбрасывает обращение и вводит в заблуждение

- **Место:** `components/ConsultForm.tsx:1-14` (используется в `app/page.tsx:112`, `app/contacts/page.tsx:28`).

Это и UX-дефект, и юридический риск (введение в заблуждение относительно услуги; **ст. 18 152-ФЗ** — оператор обязан разъяснить порядок обработки до её начала, а тут обработка лишь имитируется).
- **Фикс:** до появления бэкенда — честный фолбэк: кнопка `mailto:` с подстановкой темы/текста + видимый статус «форма не отправляет данные, позвоните / напишите на …»; добавить ссылку на `/docs/politika.pdf` у чекбокса; `maxLength` полям (имя 100, контакт 100, вопрос 2000); явное сообщение после submit.

### MEDIUM-4. Правам MySQL-пользователя недостаёт гигиены наименьших привилегий (фактические гранты не проверены)

- **Место:** `db/README.md:11` (комментарий «все права на базу hkoop»), `lib/db.ts:3-16`.
- **Проверка (инспекция кода; честная оговорка):** все 10+ вызовов `q()` по проекту — только `SELECT`; пул в `lib/db.ts` используется исключительно серверными компонентами чтения. Фактические гранты командой не проверялись (выходит за разрешённый read-only режим работы с БД), единственное свидетельство — комментарий в `db/README.md:11`, который может быть устаревшим (`db/README.md:25` отмечает, что сайт пока читает `data/*.json`). Поэтому это не констатация нарушения, а гигиеническая рекомендация по глубине защиты.
- **Факт:** если пользователь приложения действительно имеет `ALL`, то достаточно одной будущей SQL-инъекции (или компрометации dev-машины) для записи/удаления при приложении, которому нужен только `SELECT`.
- **Фикс:** проверить `SHOW GRANTS` вручную вне аудита; при подтверждении — `GRANT SELECT ON hkoop.*` отдельному пользователю для сайта, миграции и сиды — отдельным привилегированным пользователем; зафиксировать это в `db/README.md` (без паролей).

- Фактические гранты MySQL-пользователя и содержимое истории git сверх `ls-files` не извлекались; секреты не использовались, кроме штатного подключения пула приложением.
- CVE-применимость оценена по бюллетеням для линейки 14.2.x; активная эксплуатация не тестировалась — вывод строится на версии пина и отсутствии патчей.
- Содержимое `politika.pdf` по существу (покрытие 152-ФЗ, реквизиты оператора, трансграничность, сроки) не оценивалось попунктно — только доступность файла и ссылки на него; перед продом нужен отдельный юридический разбор текста политики.
- Полное соответствие ГОСТ Р 52872-2019 и ERIR-маркировка при появлении рекламных текстов требуют отдельных экспертиз.

## Вердикт одной строкой

Показывать людям можно только после HIGH-блока: сначала сменить слитые в git пароли БД, затем починить согласие на Метрику/cookie и компенсировать отсутствие заголовков через meta (или сменой хостинга), параллельно обновив `next` — остальное (allowlist для `src`, честная форма, права БД до `SELECT`, урезанный поисковый индекс с `robots.txt`, реестр согласий книги почёта) вторым эшелоном.
