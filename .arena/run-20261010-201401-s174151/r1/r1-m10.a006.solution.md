# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Дата: 10.10.2026. Объект: рабочее дерево `hkoop-site` (ветка `backup-2026-10-10`), dev http://localhost:3100. Проект не менялся: только чтение кода и безопасные GET-пробы. Секреты не печатаются. Язык отчёта — русский.

## Допущения

1. Прод — статический экспорт (`output: export` при `STATIC_EXPORT=1`) на GitHub Pages; часть выводов проверена на dev-сервере и явно помечена. Следствие: секция `headers()` из `next.config.js` в проде игнорируется, GitHub Pages средствами репозитория кастомные заголовки не задаёт.
2. В проекте нет `middleware.*` и нет `app/api/**` (мутаций на сервере нет) — это ограничивает эксплуатируемость ряда CVE рантайма в проде, но не снимает supply-chain риска сборки/dev.
3. Счётчик Метрики через `NEXT_PUBLIC_YM_ID` в проверяемом окружении не задан (живая проба ниже): трекер сегодня не грузится; дефект согласия — латентный, сработает при задании переменной.
4. Пароли в `db/README.md` приняты как есть из файла (не вводились никуда); phpMyAdmin проверен только безопасным GET без попыток входа.
5. CVE-данные — по открытым бюллетеням Next.js (проверка версии в `package.json`, без установки пакетов).

## Как читать отчёт

Каждая находка: severity → место → проверка (команда и вывод/цитата) → факт → фикс (описать, не применять). Юридические пункты содержат статью НПА. В конце — чек-лист покрытия требований и вердикт одной строкой.

## HIGH

### H1. Пароли БД открытым текстом в дереве репозитория
- **Место:** `db/README.md:8-11,20,22`; дубль в `docs/ИНСТРУКЦИЯ-ПРЕСС-СЛУЖБЕ.md:28`.
- **Проверка (инспекция):** файлы лежат в рабочем дереве рядом с кодом и содержат логин/пароль root и `hkoop` + готовые команды `mysql -u hkoop -p'...'`. `.gitignore:1-8` закрывает только `.env`/`.env.local`, но не эти `.md`.
- **Факт:** любой `git push`/копия архива уносит секреты; после утечки обязательна ротация. То, что «пароли только локальные», не снимает риска: dev-пароли имеют свойство переезжать в прод.
- **Фикс (долговечный):** вынести секреты из обоих `.md` в `.env.local` (уже gitignored), в документации оставить плейсхолдеры вида `mysql -u $DB_USER -p"$DB_PASS"`; сменить оба пароля; проверить историю git (`git log -p -- db/README.md`) и при наличии ушедших коммитов считать скомпрометированными; добавить pre-commit-хук на секреты (gitleaks).

### H2. Нет охранных HTTP-заголовков; для GitHub Pages фикс — только на уровне хостинга/прокси
- **Место:** `next.config.js:1-27` (секции `headers()` нет); эффект — все URL сайта.
- **Проверка (живая проба, dev):**
  ```
  urllib.request.urlopen('http://localhost:3100/').headers
  → Vary, Cache-Control: no-store/must-revalidate, Content-Type: text/html; charset=utf-8, Date
  → X-Powered-By: нет (держится); CSP: нет; X-Frame-Options/frame-ancestors: нет; X-Content-Type-Options: нет; Referrer-Policy: нет
  ```
- **Факт:** сайт можно встраивать в чужой `iframe` (кликджекинг формы/баннера), нет барьера для инлайн-скриптов и сниффинга типов. Честная оговорка: на dev (`localhost`) сетевая угроза минимальна; для прод-экспорта на GitHub Pages заголовки средствами репозитория не задаются (`headers()` из `next.config.js` при `output: export` игнорируется, файл `_headers` — механизм Netlify/Cloudflare Pages, а не GitHub Pages).
- **Фикс:** задавать политику вне репозитория: вынести прод за Cloudflare (Transform Rules / `_headers` на Cloudflare Pages) либо на хостинг с поддержкой заголовков: `Content-Security-Policy: default-src 'self'; script-src 'self' https://mc.yandex.ru https://yandex.ru; frame-src https://yandex.ru; img-src 'self' data: https:; object-src 'none'; frame-ancestors 'self'` (уточнить под Метрику/карты), плюс `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, HSTS на прод-домене. Параллельно — кодовые mitigation, работающие и на статике: `rel="noreferrer noopener"` на внешних ссылках, `sandbox`+`referrerpolicy` на iframe (см. M3, L2), клик-ту-загрузка карты (см. M2).

### H3. Next.js 14.2.5 с известными CVE — обновить (HIGH, а не CRITICAL: прямого серверного вектора в проде сегодня нет)
- **Место:** `package.json:12` (`"next": "14.2.5"`), рядом `react: 18.3.1`, `mysql2: ^3.24.5`.
- **Проверка (инспекция кода):** версия зафиксирована `14.2.5` (август 2024), Dependabot/renovate-конфига нет. Подтверждено отсутствие `middleware.*` и пустота `app/api/**` — вектора CVE-2025-29927 (обход авторизации через `x-middleware-subrequest`, требует middleware) в проде эксплуатировать негде; собранный статический экспорт — HTML/CSS/JS без Next-сервера, dev слушает только localhost:3100.
- **Факт:** прямое RCE/обход в проде сегодня недоказуемы, поэтому CRITICAL был бы завышением. Но риск реален как supply-chain: сборка и dev-сервер крутятся на уязвимом рантайме (бюллетени ветки 14.2.x — CVE-2025-29927 до 14.2.25/15.2.3, семейство cache-poisoning/DoS CVE-2024-46982, CVE-2024-39332, закрывавшиеся в 14.2.9–14.2.15), а любое будущее middleware/API унаследует дыру молча.
- **Фикс (долговечный):** поднять `next` минимум до `14.2.33+` (или 15.x LTS), затем `react/react-dom` до свежих 18.x, прогнать `npx tsc --noEmit` и `STATIC_EXPORT=1 npm run build`; включить регулярные обновления (Dependabot monthly + `npm audit` в CI). Диапазон `^` для `next` без lock-контроля не расширять.

## LOW

### L1. Два img-src из БД без allowlist (defense-in-depth, эксплуатируемого PoC нет)
- **Место:** `app/honor/page.tsx:14` (`<img src={h.photo}>`); `components/PartnersStrip.tsx:11` (`<img src={p.logo}>`).
- **Проверка (инспекция):** соседние рендеры фильтруются (`safeHref(p.url)`, `safeHref(file_local)`), а эти два `src` — нет. Честная оговорка: эксплуатируемого XSS здесь не показано — React экранирует атрибуты, а современные браузеры не исполняют `javascript:` в `<img src>`; это отсутствующий второй рубеж на случай компрометации БД (битые/чужие пути, мусор), а не активная дыра.
- **Факт:** при правке БД сюда ляжет чужой/битый путь без валидации, тогда как `<a href>` уже закрыт. Партнёр с IDN-доменом (`хабаровсккурорт.рф`) подтверждает: внешние/юникод-URL реально идут из БД и должны валидироваться везде одинаково, но грубое применение нынешнего `safeHref` (только `https?://` и `/[^/\\]`) их может сломать — нужен аккуратный хелпер.
- **Фикс:** ввести `safeSrc` рядом с `safeHref` (allowlist `https?://` + site-relative, `encodeURI`-нормализация кириллицы, проверка на живых примерах IDN/кириллических путей), при `null` — плейсхолдер со звездой (как уже есть в honor); добавить `referrerPolicy="no-referrer"` для внешних логотипов.

### L2. Внешние ссылки партнёров: явного `noopener` нет (в современных браузерах закрыто через `noreferrer`); партнёрский блок — информационный
- **Место:** `components/PartnersStrip.tsx:29`; `app/page.tsx:95`; проба: `GET /partners → 200; noreferrer=13, noopener=0, _blank=13`.
- **Проверка:** оговорка честно: по спецификации HTML `rel="noreferrer"` в современных браузерах включает поведение `noopener` (reverse-tabnabbing закрыт); явный `noopener` — лишь defense-in-depth для старых движков. `safeHref` пускает любой `https://` — доверенный блок «Полезные ссылки» может увести на фишинг при правке БД.
- **НПА (смежно):** ст. 10 Закона № 149-ФЗ (достоверность); партнёрский блок сейчас информационный (без «купить/скидка», без трекеров), маркировка по ст. 18.1 Закона № 38-ФЗ не требуется, но это надо зафиксировать регламентом.
- **Фикс:** `rel="noreferrer noopener"` везде с `_blank` (дешёвый второй рубеж); в админ-регламенте зафиксировать «партнёрские ссылки — некоммерческие, без вознаграждения»; при появлении платных размещений — пометка «Реклама» + erid по ст. 18.1 Закона № 38-ФЗ.

### L3. PDF-превью без песочницы; внешний https допустим как src iframe
