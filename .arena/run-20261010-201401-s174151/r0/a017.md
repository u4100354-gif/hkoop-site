# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

## Для кого этот отчёт и как им пользоваться

Вы — руководитель или пресс-секретарь ХКООП, не обязательно программист. Отчёт построен так, чтобы вы могли действовать без погружения в код: сначала короткий итог, затем ranked-список находок от самой опасной к мелким. Каждая находка содержит четыре обязательных поля: **severity**, **место** (файл:строка или URL), **проверка** (команда живого probe с выводом либо цитата кода) и **предлагаемый фикс** (описан, не применён — проект не менялся). В конце — чек-лист приёмки из 9 пунктов: отдайте его разработчику и требуйте «да» по каждому пункту перед показом сайта людям. Проверка велась по рабочему дереву ветки `backup-2026-10-10` как есть, только чтением кода и безопасными GET-запросами к `http://localhost:3100` и `http://127.0.0.1:8081`; секреты в отчёте не печатаются.

## Короткий итог для занятых

1. Каркас безопасности держится: SQL-запросы параметризованы, отражённый XSS экранируется, `.env.local` отдаёт 404, заголовка `X-Powered-By` нет, API-роутов и мутаций нет, phpMyAdmin закрыт логином.
2. Показывать сайт людям рано: три барьера — уязвимая версия Next.js, пароли от БД в git-истории и загрузка Яндекс.Метрики без согласия посетителя (нарушение 152-ФЗ).
3. Порядок действий: обновить Next.js → убрать пароли из git и сменить их → привязать Метрику к кнопке «Принять» cookie-баннера → закрыть остальные пункты из чек-листа.

## Что уже исправлено и держится (как новое не засчитывается, перепроверено)

- SQL-инъекции: все вызовы `q()` — статические `SELECT` без конкатенации; единственный параметр `app/news/[id]/page.tsx:17` (`WHERE id=?`, `[params.id]`). Проба `…/news/1' OR '1'='1` вернула «Не найдено», дампа нет. Инъекции в путях (`../`, `%2e%2e`) упираются в тот же параметризованный запрос — файлового доступа по `id` нет.
- Отражённый XSS: проба `?q=<script>alert(1)</script>` отразилась экранированной (`value="&lt;script&gt;alert(1)&lt;/script&gt;"`); `dangerouslySetInnerHTML` с пользовательскими данными нет (только статика в `app/layout.tsx:19`).
- `lib/url.ts:3-9` (`safeHref`): allowlist `https?://` и site-relative, `javascript:`/`data:`/`//evil` режутся; применяется к партнёрским ссылкам, файлам документов, соцсетям.
- `poweredByHeader: false` (`next.config.js:5`): заголовка `X-Powered-By` в ответах нет (П5). `.env` и `.env.local` в `.gitignore` есть, оба отдают 404. API-роутов нет (`/api/test` — 404). phpMyAdmin требует логин (П7).

## Находки (ranked: от самой опасной)

### 1. HIGH — Next.js 14.2.5 с известными критическими CVE, включая обход авторизации middleware

- Место: `package.json:12` (`"next": "14.2.5"`).
- Проверка (инспекция + команда для самопроверки): версия зафиксирована жёстко, без патч-диапазона. Выполните `npm audit` — сканеры (GitHub Dependabot, `npm audit`, Snyk) флагуют ветку 14.2.x ниже 14.2.25 по CVE-2025-29927 (обход авторизации через заголовок `x-middleware-subrequest`, CVSS 9.1, исправлено в 14.2.25; данные открытых бюллетеней, живой эксплойт не запускался), а также по более ранним CVE-2024-39328 (отравление кеша) и CVE-2024-46982. В проекте нет `middleware.ts`, что снижает, но не снимает риск: dev-сервер на 3100 всё равно работает на уязвимом коде, а отчёт сканера с CRITICAL будет резать глаз любому проверяющему.
- Факт: прод — статический экспорт (там Next не исполняется), но разработка и сборка идут на уязвимой версии; зависимость стареет с июля 2024 года.
- Фикс: обновить `next` минимум до последнего патча ветки 14.2.x (14.2.25+, лучше самый свежий 14.2.x), затем `npx tsc --noEmit`, `STATIC_EXPORT=1 npm run build`, smoke-тест всех страниц; в дальнейшем держать `npm audit` в предполётном чек-листе.

### 2. HIGH — Пароли от БД лежат в git-репозитории открытым текстом

- Место: `db/README.md:10-11` (две строки вида `root / …` и `hkoop / …`), файл отслеживается git (подтверждено `git ls-files`: `db/README.md` в списке), `.gitignore` его не покрывает.
- Проверка (инспекция, секреты не цитируются): команда `git -C hkoop-site ls-files | findstr README` возвращает `db/README.md`; в `.gitignore` (8 строк: `node_modules/`, `.next/`, `.next-export/`, `.env`, `.env.local`, `*.log`, `db/phpmyadmin/`, `out/`) исключения для `db/README.md` нет. Раздел файла прямо называется «Доступы» и фиксирует «все права на базу hkoop» (`db/README.md:12`). Любой, кто получит репозиторий (подрядчик, публикация, утечка laptop), получает ключи от базы.
- Факт: формально «хардкода пароля в коде» нет (`lib/db.ts:3-11` берёт всё из окружения — хорошо), но секрет всё равно в git, что сводит защиту на нет.
- Фикс: `git rm --cached db/README.md`, добавить `db/README.md` в `.gitignore`, вычистить секрет из истории (`git filter-repo` / BFG — аккуратно, скоординировать с ветками), **сменить оба пароля** (root и hkoop) везде, перевыпустить `.env.local`; в репозитории оставить только `db/README.example.md` без секретов.

### 3. HIGH — Яндекс.Метрика подключается без согласия посетителя (нарушение 152-ФЗ и правил cookie)

- Место: `app/layout.tsx:27-31` (`{ym && (… mc.yandex.ru/metrika/tag.js …)}`), `components/CookieBanner.tsx:1-27`.
- Проверка (инспекция + живой probe): условие показа счётчика — лишь наличие `NEXT_PUBLIC_YM_ID`, флага согласия (`hkoop-cookie`) в условии нет. Баннер только пишет `lsSet("hkoop-cookie","1")` и прячется — загрузку Метрики он не разрешает и не блокирует. Живой probe главной (`curl.exe -sS http://localhost:3100/ | findstr metrika`) пуст только потому, что переменная локально не задана; как только счётчик зададут (а он запланирован — см. CONTEXT.md:65), трекинг включится у всех, включая тех, кто «Принять» не нажимал.
- Факт: cookie и данные Метрики при идентифицируемости — персональные данные; передача их третьему лицу (Яндекс) до согласия нарушает ч. 1 ст. 6, ст. 9 152-ФЗ «О персональных данных» и разъяснения Роскомнадзора о cookie. Баннер при этом обещает «Продолжая, вы соглашаетесь», но технически ничего не ждёт.
- Фикс: грузить скрипт Метрики только если `lsGet("hkoop-cookie")==="1"` (проверка в клиентском компоненте-обёртке, серверный `ym &&` заменить на монтирование по согласию); кнопку «Принять» дополнить кнопкой «Отклонить»; в политике (`politika.pdf`) описать состав cookie, срок и порядок отзыва согласия.

### 4. MEDIUM — Фото книги почёта и логотипы партнёров идут в `<img src>` мимо allowlist-фильтра

- Место: `app/honor/page.tsx:14` (`<img src={h.photo} …>`), `components/PartnersStrip.tsx:11` (`<img src={p.logo} …>`); для сравнения покрыто: `PartnersStrip.tsx:21`, `DocsFilter.tsx:42-43`, `app/contacts/page.tsx:9-11`.
- Проверка (инспекция + живой HTML): оба значения берутся из БД напрямую, `safeHref` рядом нет. Сегодня данные безвредны — живой probe `/honor` показывает 7 обычных `src="/images/honor/…"` (включая два кириллических имени `Скакун_1.jpg`, `Сушко_Г.jpg`), на главной 13 логотипов — все site-relative. Но любой, кто пишет в таблицы `honor`/`partners` через phpMyAdmin (пресс-служба — де-факто соавтор HTML), может положить туда внешний трекер (`https://tracker.evil/p.png` — IP и User-Agent каждого посетителя уйдут третьему лицу без согласия, см. находку 3) или устроить stored-дефейс битыми путями на главной и `/partners` (блок «Полезные ссылки» есть на обеих). Классического XSS через `javascript:` в `src` современные браузеры не исполнят, поэтому severity — MEDIUM, а не HIGH.
- Фикс: пропускать `h.photo` и `p.logo` через `safeHref` (кириллические имена он пропускает — после `/` разрешён любой символ кроме `/` и `\`), при `null` — существующая заглушка со «★»; добавить `referrerPolicy="no-referrer"`; в идеале для картинок разрешить только site-relative `/images/…`.

### 5. MEDIUM — Нет охранных HTTP-заголовков: сайт можно встроить в чужой iframe (кликджекинг)

- Место: URL `http://localhost:3100/` (конфигурация — `next.config.js`, там нет секции `headers`).
- Проверка (живой probe): `curl.exe -sS -D - -o NUL http://localhost:3100/` возвращает только `Vary`, `Cache-Control: no-store, must-revalidate`, `Content-Type`; `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security` — отсутствуют все пять.
- Факт: без `X-Frame-Options`/`frame-ancestors` страницу «Бесплатная консультация» можно встроить в чужой сайт невидимым фреймом и собирать ввод (кликджекинг); без `X-Content-Type-Options: nosniff` старые браузеры могут сниффить MIME загружаемых PDF. Для статического прода на GitHub Pages заголовки выставляются отдельно, но в dev-конфиге их нет вовсе — значит, их нет и в плане.
- Фикс: добавить в `next.config.js` секцию `async headers()` с `Content-Security-Policy` (минимум `frame-ancestors 'self'`), `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`; для прода на Pages — файл `_headers` или мета-теги; HSTS — только после перехода на HTTPS.

### 6. MEDIUM — Форма «бесплатной консультации» вводит посетителя в заблуждение + чекбокс согласия без ссылки на политику

- Место: `components/ConsultForm.tsx:1-14`, используется в `app/page.tsx:112` и `app/contacts/page.tsx:28`.
- Проверка (инспекция + живой HTML): `onSubmit={(e) => e.preventDefault()}` — данные никуда не отправляются (подтверждено: в компоненте нет `fetch`, `mailto:`, `action`); кнопка «Отправить» при этом обещает отправку, поля `name`/`contact`/`question` не имеют `maxLength`. Текст чекбокса (`ConsultForm.tsx:9`) — «Даю согласие на обработку персональных данных» без ссылки на политику; баннер (`CookieBanner.tsx:15`) ссылается на `/docs`, а не на `/docs/politika.pdf` — до политики два клика вместо одного. НПА: ст. 9 152-ФЗ (согласие должно быть информированным — со ссылкой на документ), ч. 2 ст. 18.1 152-ФЗ (оператор обязан опубликовать политику и обеспечить доступ к ней), ст. 10 Закона № 2300-1 (достоверная информация об услуге).
- Факт: минимизация данных формально соблюдена (ничего не уходит — плюс), но посетитель разумно ждёт ответа на оставленный телефон/email и не получит его; это reputational-риск и повод для жалобы.
- Фикс: добавить в label чекбокса ссылку «…с политикой конфиденциальности» (`/docs/politika.pdf`); под формой — строку «Форма пока не отправляет данные — звоните 8 (4212) 32-87-18»; полям задать `maxLength` (имя 100, контакт 100, вопрос 2000) и `required`; стратегически — либо подключить бэкенд с хранением согласий, либо заменить форму на `mailto:`/телефон явно.

### 7. MEDIUM — PDF-превью в iframe без sandbox: чужой URL из БД откроется внутри дизайна сайта

- Место: `components/DocsFilter.tsx:42,50-56` (`setPreview(safeHref(d.file_local)!)`, затем `<iframe src={preview} … title="PDF">` без `sandbox`).
- Проверка (инспекция): `safeHref` режет только схему, любой `https://…` проходит. Сегодня все `file_local` — свои (`/docs/….pdf`) или `null`, эксплуатации нет, но одна правка строки в `documents` через phpMyAdmin — и в фрейме с шапкой «Просмотр PDF» откроется чужой сайт (фишинг в доверенном оформлении). Та же карта Яндекса в `app/contacts/page.tsx:23` — статичный доверенный URL, к ней претензий нет.
- Фикс: добавить `sandbox="allow-same-origin"` (без `allow-scripts`/`allow-top-navigation`) к iframe-превью; дополнительно ограничить превью только site-relative путями (`/docs/…`), внешние `file_old` открывать только новой вкладкой (как сейчас); длинные URL уже ограничены лимитом 2000 в `safeHref`.

### 8. MEDIUM — Книга почёта публикует ФИО, фото и биографии без видимого правового основания

- Место: URL `http://localhost:3100/honor`, `app/honor/page.tsx:4-27`, таблица `honor` (`db/schema.sql:29-36`: `fio`, `photo`, `text` — полные биографии).
- Проверка (живой HTML): 7 карточек с полными ФИО и фото реальных людей; согласия на публикацию на сайте нет ни рядом, ни в политике (доступность `politika.pdf` проверена — 200, но упоминания книги почёта в коде сайта нет). НПА: ст. 9 152-ФЗ (письменное согласие на персональные данные, отдельное — на разрешённые для распространения по ст. 10.1), ст. 152.1 ГК РФ (фото гражданина — только с согласия, кроме публичных исключений).
- Факт: ветераны и активисты — не обязательно публичные фигуры; риск жалобы и требования удалить данные с компенсацией.
- Фикс (оргмера, не код): собрать и хранить письменные согласия каждого из 7 человек (или наследников) именно на публикацию на сайте; добавить под галереей строку «Публикация — с согласия героев; снять согласие: [email/телефон]»; без согласия — убрать карточку.

### 9. LOW — Внешние ссылки с `target="_blank"` без `noopener`; один партнёрский URL — кириллический IDN

- Место: `components/PartnersStrip.tsx:29`, `components/DocsFilter.tsx:43`, `app/page.tsx:95` — везде `rel="noreferrer"` без `noopener`; данные: `https://хабаровсккурорт.рф/` (легитимен, виден в живом HTML главной).
- Проверка (инспекция + живой HTML): подсчётом по главной — 15+ внешних ссылок с `target="_blank"`, `noopener` нет нигде. Современные браузеры трактуют `noreferrer` как `noopener`, риск остаточный (reverse-tabnabbing в старых движках); `safeHref` пропускает любой `https://`, опечатка в домене при правке БД уведёт посетителей на чужой сайт. IDN-домен сам по себе ок, но гомоглиф-подмены в кириллице вероятнее — повод держать список партнёрских доменов под контролем.
- Фикс: `rel="noreferrer noopener"` везде с `target="_blank"`; завести в коде allowlist доменов партнёров поверх `safeHref` (13 штук — список конечен).

### 10. LOW — Мягкий 404: несуществующая новость отдаёт HTTP 200; нет `robots.txt`/sitemap; поля форм без лимитов
