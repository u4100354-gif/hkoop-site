# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Дата: 10.10.2026. Объект: `hkoop-site`, рабочая ветка `backup-2026-10-10` (рабочее дерево как есть), Next.js 14.2.5 + React 18 + MariaDB `hkoop`. Живые пробы — только безопасные GET к `http://localhost:3100` и `http://127.0.0.1:8081`. Проект не менялся. Секреты в отчёте не печатаются.

## Допущения

- Dev-сервер на `:3100` собран из того же дерева, что и прод-экспорт (разница только в `STATIC_EXPORT`), поэтому выводы по коду переносимы на прод.
- Компонента `SearchClient` в репозитории нет — поиск реализован парой `components/HeaderSearch.tsx` + `app/search/page.tsx`; проверены оба.
- Содержимое `public/docs/politika.pdf` по существу (полнота политики) и точная версия phpMyAdmin не аудировались — проверены доступность, ссылка и факт логина.
- CVE по `next` приведены по публичным GitHub Security Advisories (сеть для перепроверки была недоступна — сверено с памятью advisories, формулировки осторожные).

## Что проверено и держится (ранее исправленное — как новое не засчитывается)

- Все вызовы `q()` — статические строки без конкатенации; единственный параметр (`app/news/[id]/page.tsx:17`, `WHERE id=?`) идёт через placeholder. Живой probe `/news/1' OR '1'='1` → 200 «Не найдено», без ошибок БД.
- `lib/url.ts` (allowlist `http(s)` + site-relative) применён ко всем href из БД (партнёры, соцсети) и к iframe-превью PDF.
- `poweredByHeader: false` (`next.config.js:5`); живой probe `/` → заголовка `X-Powered-By` нет.
- `/.env.local` → 404, `/package.json` → 404, `/.env.example` → 404.
- Отражённый XSS в `/search?q=`: payload `<script>alert(1)</script>` вернулся экранированным (`value="&lt;script&gt;alert(1)&lt;/script&gt;"`), кавычки — как `&quot;`; скрипт не исполняется (React-эскейпинг + `defaultValue`). Аналогично в `HeaderSearch` нет `innerHTML`.
- Несуществующий `/news/nonexistent-xyz-123` и траверс `/news/%2e%2e%2f..%2fetc%2fpasswd` → штатная страница «Не найдено», без стектрейсов и деталей SQL.
- API-роутов нет (`app/**/route.ts` — пусто), мутаций из клиента нет.
- phpMyAdmin `http://127.0.0.1:8081/` отвечает страницей входа (требует логин).
- Импринт есть: адрес, телефон, email и наименование союза — в `components/Footer.tsx:6-11` и на `/contacts` (живой probe подтверждает).
- Cookie-баннер и чекбокс согласия в форме есть; политика доступна: `/docs/politika.pdf` → 200 `application/pdf`. Версия для слабовидящих работает (переключатель в шапке, классы `vi-mode`/`vi-big`/`vi-noimg` в `app/globals.css:206-212`, skip-link в `app/layout.tsx:20`).
- Данные в БД сейчас чистые: все `partners.url/logo`, `honor.photo`, `documents.file_*` соответствуют allowlist (проверено `SELECT`, посторонних схем нет).

## Находки (ранжированы)

### F1. CRITICAL — Действующие пароли БД в отслеживаемом git файле

- **Место:** `db/README.md:10-11` (строки с паролями root и hkoop; цитаты опущены намеренно).
- **Проверка (инспекция + git, только чтение):** `git ls-files db/README.md` → файл отслеживается; `git check-ignore -v db/README.md` → не игнорируется (`.gitignore` покрывает только `.env` и `.env.local`). Репозиторий публикуется на GitHub (прод — GitHub Pages), т.е. секреты уходят/ушли в удалённый репозиторий.
- **Факт:** два действующих локальных пароля (суперпользователь и пользователь приложения) лежат в коммитящемся текстовом файле рядом с инструкцией подключения. Это обнуляет половину остальных мер (логин phpMyAdmin, `.env.local` в игноре).
- **Фикс (не применять):** 1) сменить оба пароля (root и hkoop) везде; 2) убрать секреты из `db/README.md`, оставив плейсхолдеры; 3) добавить `db/README.md` в `.gitignore` либо перенести секреты в менеджер паролей; 4) вычистить историю (`git filter-repo` + force-push) и считать старые пароли скомпрометированными, отозвать там, где переиспользовались.

### F2. HIGH — Яндекс.Метрика в коде включается без проверки согласия

- **Место:** `app/layout.tsx:27-32`.
- **Проверка (инспекция + живой probe):** layout рендерит загрузчик `https://mc.yandex.ru/metrika/tag.js` всякий раз, когда задан `NEXT_PUBLIC_YM_ID`, — флаг `hkoop-cookie` из `CookieBanner` нигде не читается. Живой probe `/` в dev счётчика не нашёл (`mc.yandex.ru` отсутствует — переменной нет), т.е. утечки сейчас нет, но первая же прод-сборка со счётчиком включит трекинг до клика «Принять», прямо противореча тексту баннера («Продолжая, вы соглашаетесь»).
- **НПА:** ч. 1 ст. 9 Федерального закона № 152-ФЗ (обработка только с согласия); передача данных третьему лицу (Яндекс) без согласия — то же нарушение.
- **Фикс (не применять):** грузить `tag.js` и `noscript`-пиксель только после `lsGet("hkoop-cookie")==="1"` (клиентский гейт в отдельном `"use client"`-компоненте вместо безусловного скрипта в layout); задокументировать в политике состав данных Метрики.

### F3. HIGH — У cookie-баннера нет отказа и отзыва согласия

- **Место:** `components/CookieBanner.tsx:17-24` — единственная кнопка «Принять»; ссылка «политикой конфиденциальности» ведёт на `/docs`, а не на сам текст политики.
- **Проверка (инспекция):** обработчик только пишет `hkoop-cookie=1`; пути «Отклонить» и отзыва решения нет, срок согласия не фиксируется.
- **НПА:** ч. 1 ст. 9 Закона № 152-ФЗ (согласие должно быть конкретным, информированным и сознательным + право на отзыв, ч. 2 ст. 9); разъяснения Роскомнадзора к cookie-баннерам (вариант отказа/отзыва обязателен).
- **Фикс (не применять):** кнопки «Принять» / «Отклонить», повторный вызов через футер («Настройки cookie»), прямая ссылка на `/docs/politika.pdf`, фиксация даты/текста согласия.

### F4. HIGH — Next.js 14.2.5 с известными уязвимостями (включая критическую)

- **Место:** `package.json:12` (`"next": "14.2.5"`, август 2024).
- **Проверка (инспекция):** версия зафиксирована ниже всех последующих security-фиксов ветки 14.2.x, включая критический обход авторизации через middleware CVE-2025-29927 (CVSS 9.1, исправлено в 14.2.25) и более ранние фиксы middleware/cache (CVE-2024-39328, CVE-2024-46982).
- **Компромисс — честно:** «за» проблему: dev-сервер крутит полный Next.js, любой будущий middleware/API унаследует дыру. «Против»: в проекте нет middleware, API-роутов и авторизации, а прод — статический экспорт, т.е. прямой эксплуатации сегодня почти наверняка нет. Синтез: оставить HIGH как гигиену, а не как пожар, — чинить плановым обновлением, а не ночью.
- **Фикс (не применять):** обновить `next` до свежего 14.2.x (или 15.x) + `npm audit fix`, включить Dependabot/регулярный `npm audit` перед сборкой.

### F5. MEDIUM — У MySQL-пользователя приложения избыточные права

- **Место:** права `hkoop@localhost` (вывод `SHOW GRANTS`, получен локально, цитата пароля опущена).
- **Проверка (только SELECT):** `GRANT ALL PRIVILEGES ON hkoop.*` — включая DROP/ALTER/CREATE; при этом весь код сайта делает только `SELECT` (все страницы это подтверждают).
- **Компромисс — честно:** «за»: утечка `.env.local` или доступ пресс-службы через phpMyAdmin тем же пользователем = потеря/подмена всех таблиц. «Против»: администрирование через того же пользователя удобно, а пароль пока только локальный. Синтез: удобство не перевешивает — сайту завести `hkoop_ro` с `GRANT SELECT ON hkoop.*`, полные права оставить человеку и не хранить их в проектном `.env`.
- **Фикс (не применять):** создать read-only пользователя для `lib/db.ts`, ограничить хост, убрать `ALL PRIVILEGES` у сервисного аккаунта.

### F6. MEDIUM — Форма консультации собирает согласие, но ничего не делает и молчит

- **Место:** `components/ConsultForm.tsx:4-11` (только `preventDefault`, нет success-состояния); используется на `/` (`app/page.tsx:112`) и `/contacts`.
- **Проверка (инспекция + живой probe `/contacts`):** кнопка «Отправить» не отправляет данные и не показывает никакого сообщения; чекбокс «согласие на обработку ПДн» при этом обязателен, рядом нет ни ссылки на политику, ни наименования оператора.
- **НПА:** ч. 1, ч. 4 ст. 9 Закона № 152-ФЗ (в согласии должны быть цель, оператор, перечень действий); сбор «согласия в никуда» вводит в заблуждение. Плюс нарушение собственного процессного правила (у каждого действия — success/error).
- **Фикс (не применять):** либо честная заглушка («форма не отправляется — звоните …, ответим в часы …») + сообщение после клика, либо `mailto`/канал связи; к чекбоксу добавить ссылку на политику и наименование оператора («Союз ХКООП, адрес …»).

### F7. MEDIUM — PDF-превью без `sandbox`, источник — любой https из БД

- **Место:** `components/DocsFilter.tsx:42,56` — `preview` берётся из `safeHref(d.file_local)` (пропускает любой `https://`), `<iframe src={preview}>` без `sandbox`.
- **Проверка (инспекция + данные):** текущие строки БД безвредны (только `/docs/*.pdf` и `habprof.ru`), но одна ошибочная/вредоносная строка через phpMyAdmin встроит чужой активный контент в оформление сайта (доверие пользователя + адрес сайта в табло).
- **Фикс (не применять):** `<iframe sandbox="">` (без `allow-scripts`/`allow-same-origin`), для превью разрешить только site-relative `/docs/*.pdf`, внешние URL — только обычной ссылкой с меткой внешнего ресурса.

### F8. MEDIUM — Нет заголовков безопасности (CSP / X-Frame-Options / др.)

- **Место:** ответ `/` (живой probe): `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `HSTS` — отсутствуют; `Cache-Control: no-store, must-revalidate`.
- **Компромисс — честно:** «за»: без CSP/X-Frame-Options сайт можно встроить в чужой iframe (кликджекинг обёртки) и грузить что угодно откуда угодно. «Против»: GitHub Pages не отдаёт кастомные заголовки, а на сайте нет авторизации и денежных действий — ущерб от кликджекинга низкий. Синтез: MEDIUM, чинить тем, что доступно статике: CSP через `<meta http-equiv>`, а полный набор заголовков — при переезде на хостинг, где они настраиваются.
- **Фикс (не применять):** `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self' https://mc.yandex.ru; frame-src https://yandex.ru">` (уточнить под фактуру), `frame-ancestors 'self'`; iframe карты — с `sandbox` по минимуму.

### F9. MEDIUM — Книга почёта публикует персональные данные третьих лиц без видимого основания

- **Место:** `app/honor/page.tsx:11-22` — ФИО, фото, год, биографический текст 7 человек; источник — таблица `honor`.
- **Проверка (инспекция + SELECT):** тексты — «полные биографии», фото — локальные файлы; документов согласия в репозитории нет (их там и не должно быть, но регламента нет тоже).
- **НПА:** ст. 9 (письменное согласие, а для общедоступных данных — ст. 10.1 Закона № 152-ФЗ: согласие оформляется отдельно, с возможностью отзыва через информсистему/Роскомнадзор).
- **Фикс (не применять):** собрать/подтвердить письменные согласия на публикацию (включая фото) по ст. 10.1, хранить у оператора, в регламент пресс-службы добавить снятие с публикации по отзыву за ≤3 дней.

### F10. LOW — Два `<img>`-стока из БД идут мимо `safeHref`

- **Место:** `components/PartnersStrip.tsx:11` (`src={p.logo}`) и `app/honor/page.tsx:14` (`src={h.photo}`) — в отличие от `href`, которые фильтруются.
- **Проверка (инспекция + SELECT):** данные сейчас чистые (`/images/*`); exploit-спор — честно: «за» — нефильтрованный сток из БД; «против» — современные браузеры не исполняют `javascript:`/`data:`-SVG-скрипты в контексте `<img>`, инъекция атрибутов невозможна (React экранирует). Синтез: LOW — реальны дефейс (битая/чужая картинка) и внешний трекинг-пиксель, а не XSS. Сюда же: внешние ссылки с `target="_blank"` имеют `rel="noreferrer"` (что в современных браузерах тянет и `noopener`), но явного `noopener` нет.
- **Фикс (не применять):** `logo`/`photo` через тот же `safeHref` (+ для логотипов allowlist `/images/*`), к внешним ссылкам добавить явный `noopener` и визуальную метку внешнего перехода.

### F11. LOW — В полях ввода нет `maxLength` и типовой валидации

- **Место:** `components/ConsultForm.tsx:5-7`, фильтры (`NewsFilter`, `DocsFilter`), `app/search/page.tsx:34`.
- **Проверка (инспекция + probe длинной строки):** сегодня безопасно — бэкенда нет, React экранирует вывод, поиск клиентский. Риск отложенный: первое же API/письмо/лог без лимитов получит гипердлинные и HTML/JS-входы.
- **Фикс (не применять):** `maxLength` (имя ~100, вопрос ~2000), `autoComplete`/`inputMode` по смыслу, а при появлении бэкенда — серверная валидация и нормализация.

### F12. LOW — `.gitignore` пропускает будущие `.env.*-файлы`

- **Место:** `.gitignore:4-5` — только `.env` и `.env.local`; шаблонов `.env.*.local` / `.env.production` нет.
- **Проверка (инспекция):** следующий окруженческий файл (`.env.production.local`) уйдёт в git молча.
- **Фикс (не применять):** добавить строки `.env*.local` и `.env.production*` (или просто `.env*` с исключением `.env.example`).

### F13. LOW — Точечные gaps версии для слабовидящих и alt-текстов

- **Место:** `app/page.tsx:52` (`alt=""` у новостных миниатюр — они ссылочные, пустой alt обедняет скринридер); `components/CookieBanner.tsx:12` (`role="dialog"` без фокус-ловушки и возврата фокуса); `components/ViProvider.tsx:25-28` — режимы «крупный/без картинок» не персистятся (в отличие от самого VI-флага).
- **НПА:** ГОСТ Р 52872-2019 (требования к доступности: масштабирование, контраст, клавиатурность) — база покрыта (`vi-mode`/`vi-big`/`vi-noimg`, skip-link), это именно доделки.
- **Фикс (не применять):** осмысленные `alt` (или `alt` заголовка новости), фокус-менеджмент диалога, `lsSet` для `vi-big`/`vi-noimg`.

## Что прямо НЕ является проблемой (чтобы не чинили зря)

- Параметризация SQL — везде, включая `news/[id]`; «SQL-инъекция в `q()`» отсутствует как класс.
- Отражённый XSS через `?q=` и фильтры — экранируется React; `javascript:`/`data:` в href/iframe из БД режутся `safeHref`.
- Инъекции путей (`../`, `%2e%2e`) в `/news/<id>` — id идёт только параметром в SQL и никогда в файловую систему.
- Партнёрские ссылки — информационные (ФНПР, правительство края, фонды, вузы, надзор), признаков скрытой рекламы нет; маркировка (erid) не требуется. Логотипы/фото хранятся локально, хотлинка чужого контента нет.
- Импринт по ст. 10 Закона № 149-ФЗ (наименование, адрес, телефон, email) — присутствует.

## Вердикт одной строкой

Показывать людям можно только после F1 (сменить слитые пароли и вычистить их из git) и решения по согласию/Метрике (F2–F3), затем — обновление Next.js и урезание прав БД (F4–F5); остальное — плановые доделки.
