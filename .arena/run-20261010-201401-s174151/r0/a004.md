# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Аудит проведён по рабочему дереву ветки `backup-2026-10-10` как есть (есть незакоммиченные изменения, см. проверку П11). Проект не менялся: только чтение кода и безопасные GET-запросы к `http://localhost:3100` и `http://127.0.0.1:8081`. Записей в БД не было (ни одного INSERT/UPDATE/DELETE), пакеты не ставились, процессы не трогались. Секреты не приводятся. Отчёт на русском.

## 0. Ограничения и допущения

Жёсткие ограничения, в которых велось исследование (от самого сжимающего — дальше):

1. **Проект не менять** — только чтение и GET-пробы; фиксы ниже описаны, не применены.
2. **Пробы только безопасными GET** к dev-серверу и phpMyAdmin; без флуда, без перебора, без попыток обхода логина.
3. **Только SELECT к БД** — фактически к БД напрямую не подключались вовсе (хватило кода + HTTP-проб + `data/*.json`), права mysql-пользователя вживую не проверялись (отмечено как непроверенное, находка Л-7).
4. **Секреты не печатать** — пароли из `db/README.md` / `.env.local` не цитируются.
5. **Прод — статический экспорт** (`output: export` при `STATIC_EXPORT=1`) на GitHub Pages; dev на `:3100` — это разные режимы, оговорено в каждой находке, где важно.
6. Допущения: dev-сервер на `:3100` соответствует рабочему дереву; содержимое БД соответствует сидам (`211` новостей и т.д. по CONTEXT.md — точные counts не перепроверялись, для выводов не нужны); `NEXT_PUBLIC_YM_ID` локально не задан (подтверждено отсутствием `mc.yandex` в HTML главной, проба П10).

## 3. Находки, ranked (новое)

### С-1. HIGH — Уязвимый Next.js 14.2.5 (известные CVE, обновление назрело)
- **Место:** `package.json:12` (`"next": "14.2.5"`).
- **Проверка:** инспекция + открытые базы (NVD/GitHub Advisories). По открытым данным ветка 14.2.5 затронута как минимум: **CVE-2025-29927** (обход middleware-авторизации через заголовок `x-middleware-subrequest`, CVSS 9.1, исправлено в 14.2.25/15.2.3) и **CVE-2024-39328** (cache-poisoning DoS, исправлено в 14.2.8). Точный состав проверять командой `npm audit` при плановом обслуживании (не выполнялась — это запись чтения lock-файла, выхожу за «только чтение»? нет, `npm audit` сеть+чтение; не делалась из осторожности к запрету трогать пакеты — cat `package-lock.json` достаточно админу).
- **Факт:** фреймворк старше security-фиксов на ~год; в проекте нет middleware (эксплуатация CVE-2025-29927 здесь напрямую не видна) и прод — статика, поэтому не CRITICAL, но dev-сервер и любые будущие API/middleware унаследуют дыру.
- **Фикс (без применения):** поднять `next` минимум до `14.2.25` (или актуальный 14.x/15.x после `tsc`+регресса), зафиксировать lock-файл, включить `npm audit` в чек-лист перед каждым деплоем. Отдельно: `react 18.3.1`, `mysql2 ^3.24.5` — известных критических CVE на дату аудита не несут, обновлять паровозом не обязательно.

### С-2. HIGH — Реальные пароли БД в отслеживаемом git-файле
- **Место:** `db/README.md` (в `git ls-files` — П11; `.gitignore:1-8` его не покрывает).
- **Проверка:** файл прочитан локально (секреты не цитируются): содержит логин/пароль root и логин/пароль пользователя `hkoop` + команды заливки дампа. `git status` показывает активное рабочее дерево — файл давно в истории.
- **Факт:** секрет в системе контроля версий = компрометация при любом расшаривании/утечке репозитория; смена пароля без чистки истории не поможет.
- **Фикс:** (1) сменить оба пароля в MariaDB; (2) вычистить из истории (`git filter-repo`/`BFG`) и форс-пуш во все репозитории-клоны; (3) держать доступы только в менеджере паролей + `.env.local`; (4) добавить в `.gitignore` `db/README.md` или вынести доступы из файла в шаблон (`db/README.example.md`).

### Ю-1. HIGH — Яндекс.Метрика по коду грузится без согласия (152-ФЗ, cookie)
- **Место:** `app/layout.tsx:15,27-31` (рендер `ym(...)` при любом заданном `NEXT_PUBLIC_YM_ID`) + `components/CookieBanner.tsx:1-27` (никак не связан с загрузкой Метрики).
- **Проверка:** инспекция: условие — только наличие env, флага `hkoop-cookie` из `localStorage` никто не читает; баннер лишь пишет `hkoop-cookie=1` и прячется. Локально счётчик выключен (в HTML главной нет `mc.yandex` — П10), то есть нарушение сейчас латентное и выстрелит при включении счётчика (в `.env.example:6` он уже заготовлен).
- **Факт:** включение Метрики по этой схеме = передача cookie/IP в третью сторону до согласия. По позиции РКН cookie/аналитика — обработка ПДн: нужно предварительное согласие (ч. 1 ст. 6, ст. 9 152-ФЗ) и политика (ст. 18.1 152-ФЗ).
- **Фикс:** грузить `tag.js` и вызывать `ym(init)` только после `lsGet("hkoop-cookie")==="1"` (или cookie-флага, см. Ю-2); до согласия — никакого `noscript`-пикселя тоже; в баннере дать кнопки «Принять»/«Отклонить» и ссылку прямо на `/docs/politika.pdf`; решение хранить со сроком и возможностью отзыва (повторный вызов баннера из футера).

### С-3. HIGH — Нет заголовков безопасности (clickjacking, sniffing, CSP)
- **Место:** HTTP-ответы dev-сервера (все страницы) — проба П1.
- **Проверка:** `curl -I /` — отсутствуют `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`; `Strict-Transport-Security` отсутствует (для dev — норма, для prod-домена нужен).
- **Факт:** сайт можно встроить в чужой `iframe` (кликджекинг формы/баннера), нет защиты от MIME-sniffing, нет CSP-рамок для инлайновых скриптов (`layout.tsx:19,29` — инлайн), referrer политикой не ограничен (внешние переходы на habprof.ru/партнёров уносят полный URL).
- **Фикс:** в `next.config.js` добавить `headers()` для всех роутов: `X-Frame-Options: DENY` (или `frame-ancestors 'none'` в CSP), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, базовый `Content-Security-Policy` (с `script-src 'self' https://mc.yandex.ru` + `'unsafe-inline'` только пока живы инлайн-скрипты layout, цель — убрать инлайн вовсе), `Permissions-Policy` по минимуму; на прод-домене — `HSTS`. Учли прод-статику: для GitHub Pages заголовки задаются meta/`_headers`-аналогами или на уровне хостинга — проверить после деплоя `curl -I` прод-URL.

### С-4. MEDIUM — Фото книги почёта вставляется в `<img src>` без `safeHref`
- **Место:** `app/honor/page.tsx:14` (`<img src={h.photo} ...>` напрямую из БД) — единственное место, где данные из БД уходят в URL-атрибут мимо фильтра (партнёры — `PartnersStrip.tsx:21`, документы — `DocsFilter.tsx:42-43`, соцсети — `contacts/page.tsx:9-11` — все через `safeHref`).
- **Проверка:** инспекция + П10 (текущие значения безобидны: все `/images/honor/*`). Атака — только при контроле БД (через phpMyAdmin/дамп): `h.photo = "https://evil/..."` даст хотлинк/трекер, `data:`-схема в `img` отрендерится (современные браузеры `javascript:` в `img` не исполняют, но `data:image/svg+xml` с JS в некоторых контекстах и внешний трекинг — реальны).
- **Фикс:** `const src = safeHref(h.photo) ?? null`, при `null` — плейсхолдер-звёздочка (уже есть ветка без фото); заодно `alt={h.fio}` уже экранируется React — оставить.

### С-5. MEDIUM — `safeHref` разрешает любой http(s)-домен: компрометация строки БД = фишинговая ссылка
- **Место:** `lib/url.ts:3-9` (регулярка `^(https?:\/\/|\/[^/\\])`), потребители: `PartnersStrip`, `DocsFilter`, `contacts/page.tsx`, `app/page.tsx:37`.
- **Проверка:** инспекция: `https://anything` проходит; `rel="noreferrer"` без `noopener`/`nofollow` (`PartnersStrip.tsx:29`, `page.tsx:95`, `DocsFilter.tsx:43`); соцсети в контактах полностью из БД (`site_settings.social_vk/tg/max`).
- **Факт:** при контроле БД (тот же вектор, что С-4) любой партнер/документ/соцсеть превращается в ссылку на злоумышленника с доверием профсоюзного сайта; `noreferrer` в современных браузерах подразумевает `noopener`, но явного `nofollow`/`noopener` нет.
- **Фикс:** allowlist внешних доменов (ФНПР, госдомены `*.gov.ru`, `khabkrai.ru`, `vk.com`, `t.me`, `max.ru`, `habprof.ru`, `mc.yandex.ru` по явному списку) + `rel="noopener noreferrer nofollow"` везде наружу; смену соцсетей/партнёров логировать и подтверждать вторым лицом (регламент пресс-службы).

### Ю-2. MEDIUM — Cookie-баннер не дотягивает до согласия по 152-ФЗ
- **Место:** `components/CookieBanner.tsx:12-25`.
- **Проверка:** инспекция: только кнопка «Принять», отказа нет; ссылка «политикой конфиденциальности» ведёт на каталог `/docs`, а не на `/docs/politika.pdf`; флаг в `localStorage` (не cookie, срок не ограничен, отзыва нет); баннер клиентский (`useState`+`useEffect`) — при отключённом JS его нет вовсе, а карта на `/contacts` (см. Ю-3) трекает и так.
- **НПА:** ст. 9 (согласие должно быть конкретным и отзывным), ст. 18.1 152-ФЗ (политика и сведения об обработке cookie); позиция РКН — cookie-файлы при идентификации = ПДн.
- **Фикс:** «Принять»/«Отклонить» + ссылка прямо на `politika.pdf` (+ раздел про cookie/метрику внутри политики); хранить выбор с датой/версией текста; кнопка «Настройки cookie» в футере для отзыва; до выбора — не грузить ничего стороннего (см. Ю-1, Ю-3).

### Ю-3. MEDIUM — Яндекс-карта на `/contacts` грузится без согласия и без заглушки
- **Место:** `app/contacts/page.tsx:23` (`<iframe src="https://yandex.ru/map-widget/...">` безусловно).
- **Проверка:** инспекция + П10 (iframe присутствует в SSR-HTML страницы контактов) — запрос к `yandex.ru` с IP/User-Agent уходит при простом открытии страницы.
- **Факт:** передача технических данных третьей стороне до согласия; тот же класс нарушения, что Ю-1, но вес ниже (один iframe, не сквозной счётчик). НПА те же: ст. 6, 9, 18.1 152-ФЗ.
- **Фикс:** click-to-load: статическая заглушка (адрес + «Показать карту») → iframe только после клика/согласия; добавить `loading="lazy"` и `referrerpolicy="no-referrer"` (сейчас нет), `sandbox` по минимуму совместимому; описать в политике.

### Ю-4. MEDIUM — Форма консультации: согласие есть, но формальное; отправка молча глотается
- **Место:** `components/ConsultForm.tsx:4-12` (используется на главной `app/page.tsx:112` и в контактах `contacts/page.tsx:28`).
