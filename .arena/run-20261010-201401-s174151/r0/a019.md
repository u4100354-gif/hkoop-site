## Проверено — держится (ранее исправленное, перепроверено)

- SQL: все вызовы `q()` — либо статические строки без конкатенации пользовательского ввода, либо `WHERE id=?` с параметром. Проверены: `app/page.tsx:33-35`, `app/news/page.tsx:6`, `app/news/[id]/page.tsx:12,17`, `app/docs/page.tsx:6`, `app/partners/page.tsx:6`, `app/honor/page.tsx:5`, `app/contacts/page.tsx:7`, `app/events/page.tsx:5`. ### M5. MEDIUM — Два `img src` из БД идут мимо allowlist (хранимый вектор при компрометации БД)
- Место: `app/honor/page.tsx:14` (`<img src={h.photo} ...>`), `components/PartnersStrip.tsx:11` (`<img src={p.logo} ...>`).
- Проверка (инспекция): все href/iframe из БД проходят `safeHref`, а эти два `src` — нет. Остальной рендер БД-полей — текстовые узлы React (экранируются), это смягчает общую картину.
- Факт (честно о тяжести): в современных браузерах `javascript:` в `<img src>` не исполняется, а SVG со скриптом через `<img>` не выполняет скрипты — поэтому это НЕ готовый stored-XSS, и severity не завышается. Реальные риски: подмена логотипа/фото на внешний URL (фишинг доверия, трекинг-пиксель с IP посетителей), `data:`-мусор, поломка вёрстки; плюс ловушка для следующего разработчика («раз фото можно напрямую, то и ссылку можно»).
- Фикс (долговечный): ввести в `lib/url.ts` рядом с `safeHref` функцию `safeImgSrc` (разрешить только site-relative `/images/...` + явный allowlist CDN-доменов при нужде; `http(s)` общего вида для картинок — запретить по умолчанию), применить в обоих местах с fallback-плейсхолдером (как уже сделано через `onError` в `PartnersStrip`); добавить unit-тесты на `safeHref`/`safeImgSrc` (`javascript:`, `data:`, `//evil`, `/ok`, `https://ok`).
