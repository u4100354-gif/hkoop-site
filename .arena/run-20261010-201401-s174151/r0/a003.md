# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Аудит проведён по рабочему дереву ветки `backup-2026-10-10` как есть, без изменений проекта, БД (только `SELECT`), git, пакетов и процессов. Живые пробы — только безопасные `GET` к `http://localhost:3100` и `http://127.0.0.1:8081`. Секреты не печатаются. Проект не менялся.

## Допущения

1. Прод — статический экспорт (`output: export`) на GitHub Pages; серверного рантайма в проде нет, поэтому часть находок бьёт по dev-серверу, сборке и будущему SSR.
2. БД правит доверенный администратор через phpMyAdmin; модель угроз для хранимых данных — компрометация учётки/ошибка оператора, а не внешний злоумышленник с записью.
3. Тексты НПА цитируются по смыслу; точные пункты указаны у каждой юридической находки.

## Проверено — держится (как новое не засчитывается)

Инъекция в путях (`/news/..%2f..%2fetc%2fpasswd`, `/news/<script>alert(1)</script>`) → «Не найдено»/`404`, чтения файлов нет, в исполняемом HTML-контексте полезная нагрузка не отражена (строка `alert(1)` видна только внутри JSON RSC-пейлоада `initialCanonicalUrl`, что не исполняется).

## Находки (ранжированный список)

### CRITICAL-1. Уязвимый рантайм: `next 14.2.5` с известными CVE

- **Место:** `package.json:12` (`"next": "14.2.5"`).
- **Проверка (инспекция кода + сверка с бюллетенями):** зафиксирован пин `14.2.5` — версия старше всех крупных security-релизов ветки 14.2.x. Публичные CVE этой линейки: **CVE-2025-29927** (обход авторизации через заголовок `x-middleware-subrequest`, CVSS 9.1, исправлен в 14.2.25), **CVE-2024-46982 / CVE-2024-39332** (cache-poisoning/DoS, исправлены в 14.2.9+). Смягчает то, что `middleware.*` в проекте отсутствует и прод — статика, но dev-сервер (`localhost:3100`), сборка и любой будущий SSR/API используют уязвимый рантайм.
- **Факт:** зависимость с известными критическими уязвимостями тянется в цепочку сборки и dev-окружение; любой сканер зависимостей провалит комплаенс.
- **Фикс (описать, не применять):** поднять `next` минимум до `14.2.25`, лучше до последнего патча ветки 14.2.x; прогнать `npm audit`, пересобрать статику, перепроверить живые пробы из этого отчёта.

### HIGH-1. Пароли БД лежат в git: `db/README.md` закоммичен и не покрыт `.gitignore`

- **Место:** `db/README.md:8-12`, `.gitignore:1-8`.
- **Проверка (инспекция + read-only git):** `git ls-files db/README.md` → файл отслеживается; `.gitignore` его не покрывает; внутри — пароли root и пользователя БД в открытом виде. `.env.local` при этом не отслеживается (корректно).
- **Факт:** секрет уже в истории репозитория — удаление файла из дерева его не уберёт; любой клон/форк/утечка токена раскрывает доступ к СУБД.
- **Фикс:** срочно сменить оба пароля; вычистить файл из истории (`git filter-repo`/`BFG`) с координацией всех клонов; переписать `db/README.md` на плейсхолдеры; добавить `db/README.md` (или вынести секреты из него) в `.gitignore`; хранить доступы только локально.

### HIGH-2. У MySQL-пользователя приложения избыточные права

- **Место:** `db/README.md` (заявление «все права на базу hkoop»), `lib/db.ts:3-16`.
- **Проверка (инспекция кода):** все 10+ вызовов `q()` по проекту — только `SELECT`; пул в `lib/db.ts` используется исключительно серверными компонентами чтения. Пользователю с правом `ALL` достаточно одной SQL-инъекции в будущем (или компрометации dev-машины) для записи/удаления.
- **Факт:** нарушение принципа минимальных привилегий; глубина защиты отсутствует.
- **Фикс:** `GRANT SELECT ON hkoop.*` отдельному пользователю для сайта; миграции и сиды — отдельным привилегированным пользователем вручную; зафиксировать это в `db/README.md` (без паролей).

### HIGH-3. Нет ни одного заголовка безопасности: кликджекинг и MIME-сниффинг

- **Место:** `next.config.js:1-27` (нет секции `headers`), живой ответ сервера.
- **Проверка (живой probe):** `curl.exe -sSI http://localhost:3100/` → заголовки только `Vary`, `Cache-Control: no-store, must-revalidate`, `Content-Type`, `Date`, `Connection`. Отсутствуют: `Content-Security-Policy` (или `frame-ancestors`), `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security`.
- **Факт:** сайт можно встроить в чужой `iframe` (кликджекинг — в т.ч. вокруг формы консультации и cookie-баннера); браузеры без `X-Content-Type-Options` могут сниффить типы; при статическом экспорте заголовки через `next.config.js` вообще не выставляются — нужен отдельный механизм хостинга.
- **Фикс:** добавить файл заголовков хостинга для статики (`_headers` или эквивалент Pages): `frame-ancestors 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `HSTS` (в проде, при HTTPS), базовый `CSP` (`default-src 'self'`, `img-src 'self' data:`, `frame-src https://yandex.ru`, `script-src 'self' https://mc.yandex.ru` — после решения по Метрике); `iframe` карты и PDF-превью снабдить `sandbox`/`allow` по минимуму.

### HIGH-4. Яндекс.Метрика включается мимо согласия: баннер согласию не gating'ит

- **Место:** `app/layout.tsx:15,27-31`, `components/CookieBanner.tsx:1-27`, `lib/storage.ts:3-17`.
- **Проверка (инспекция кода + живой probe):** условие вставки Метрики — только `ym && …`, флаг `hkoop-cookie` из `localStorage` нигде не читается для этого решения; `noscript`-пиксель `https://mc.yandex.ru/watch/${ym}` — тоже безусловный. Живая проба главной сегодня не содержит `mc.yandex` (счётчик не задан — нарушения по факту нет), но достаточно задать `NEXT_PUBLIC_YM_ID` (пример с реальным ID — в `.env.example:6`), и трекер с `clickmap:true,trackLinks:true` встанет у всех посетителей до клика «Принять».
- **Факт:** разрыв между текстом согласия и фактической загрузкой трекера; включение счётчика одной переменной окружения сразу включает слежку без согласия — вопреки тексту баннера. НПА: **ст. 9, 18, 18.1 Федерального закона от 27.07.2006 № 152-ФЗ** (обработка только с согласия субъекта, информирование, политика оператора); практика РКН по cookie-баннерам (отказ должен быть не сложнее согласия).
- **Фикс:** gating'ить вставку скрипта и пикселя Метрики флагом согласия (`hkoop-cookie === "1"`), читать его до вставки; добавить в баннер кнопку «Отклонить» равного веса; ссылку в баннере вести прямо на `/docs/politika.pdf`; Яндекс-карту на `/contacts` грузить лениво после согласия (клик-плейсхолдер).

### MEDIUM-1. Два `src` из БД идут мимо allowlist: фото книги почёта и логотипы партнёров

- **Место:** `app/honor/page.tsx:14` (`<img src={h.photo} …>`), `components/PartnersStrip.tsx:11` (`<img src={p.logo} …>`).
- **Проверка (инспекция кода + SELECT-проба):** все `href`/`iframe` из БД идут через `safeHref`, а эти два `src` — напрямую. Текущие данные чистые (все 13 логотипов и 7 фото — site-relative/`https`, подозрительных схем нет). React экранирует текст, поэтому классического stored-XSS сегодня нет, но при компрометации БД в `src` ляжет `data:`/`javascript:`-значение без какого-либо барьера.
- **Факт:** неполное покрытие allowlist — единственный класс выводов из БД без фильтра.
- **Фикс:** пропускать `h.photo` и `p.logo` через `safeHref` (с запасной заглушкой как сейчас через `onError`), унифицировать с остальными выводами.

### MEDIUM-2. Форма консультации молча выбрасывает обращение и вводит в заблуждение

- **Место:** `components/ConsultForm.tsx:1-14` (используется в `app/page.tsx:112`, `app/contacts/page.tsx:28`).
- **Проверка (инспекция кода):** `onSubmit` только `preventDefault` — нет ни отправки, ни `mailto`, ни сообщений success/error, ни `maxLength` у полей; чекбокс согласия (`required`, `components/ConsultForm.tsx:8-10` — это хорошо для ст. 9 152-ФЗ) не содержит ссылки на политику.
- **Факт:** посетитель нажимает «Отправить» и обоснованно считает, что обращение ушло юристу, — оно исчезает. Это и UX-дефект, и юридический риск (введение в заблуждение относительно услуги; **ст. 18 152-ФЗ** — оператор обязан разъяснить порядок обработки до её начала, а тут обработка лишь имитируется).
- **Фикс:** до появления бэкенда — честный фолбэк: кнопка `mailto:` с подстановкой темы/текста + видимый статус «форма не отправляет данные, позвоните / напишите на …»; добавить ссылку на `/docs/politika.pdf` у чекбокса; `maxLength` полям (имя 100, контакт 100, вопрос 2000); явное сообщение после submit.

### MEDIUM-3. Cookie-баннер: нет отказа, неверная ссылка, текст врёт про Метрику

### MEDIUM-4. Поиск тащит весь корпус данных в клиентский бандл; нет `robots.txt`/sitemap

- **Место:** `app/search/page.tsx:4-5`, `components/HeaderSearch.tsx:4-5`, живой probe `GET /robots.txt` → `404` (тело — штатная страница 404).

- **Факт:** избыточное раскрытие данных (минимизация, **ст. 5 152-ФЗ** — обработка должна ограничиваться достижением целей) + нулевое управление индексацией перед продом.
- **Фикс:** генерировать урезанный `search-index.json` скриптом `scripts/gen-search-index.mjs` (заголовки + id, без полных текстов) либо серверный поиск; добавить `robots.txt` и `sitemap.xml` в `public/`.

### MEDIUM-5. Персональные данные третьих лиц без видимого учёта согласий

## Что не подтверждено (честно)

- Права MySQL-пользователя и наличие паролей в истории git проверены по файлам и read-only командам git; сами секреты не извлекались и не использовались, кроме штатного подключения пула приложением.
- CVE-применимость оценена по бюллетеням для линейки 14.2.x; активная эксплуатация не тестировалась (запрещено флудить/атаковать) — вывод строится на версии пина и отсутствии патчей.
- Содержимое `politika.pdf` по существу (покрытие 152-ФЗ, реквизиты оператора, трансграничность, сроки) не оценивалось попунктно — только доступность файла и ссылки на него; перед продом нужен отдельный юридический разбор текста политики.

## Вердикт одной строкой

Показывать людям можно только после HIGH-блока: сначала сменить слитые в git пароли БД и урезать права пользователя до `SELECT`, затем обновить `next` и починить согласие на Метрику/cookie вкупе с заголовками безопасности — остальное (allowlist для `src`, честная форма, `robots.txt`, реестр согласий книги почёта) вторым эшелоном.
