# Аудит сайта ХКООП: безопасность и соответствие законам РФ (включая 152-ФЗ)

Дата: 10.10.2026. Объект: рабочее дерево `hkoop-site` (ветка `backup-2026-10-10`), dev-сервер http://localhost:3100, phpMyAdmin http://127.0.0.1:8081. Проект не изменялся: только чтение кода и безопасные GET-пробы. Секреты не печатаются.

## Допущения

- Прод — статический экспорт (`output: export`) на GitHub Pages: серверные заголовки там недоступны, это учтено в фиксах.
- БД трогать запрещено, поэтому содержимое БД сверено через код, сиды `data/*.json` и живой рендер, а не через SELECT.
- CVE-данные — по публичным бюллетеням Next.js на дату аудита.

## Проверено и чисто (не находки)

- **SQL-инъекции отсутствуют.** Все 8 вызовов `q()` — статический SQL без конкатенации; единственный параметр (`app/news/[id]/page.tsx:17`, `WHERE id=?`) связан через placeholder. Живая проба `GET /news/1' OR '1'='1` → HTTP 200, страница «Не найдено», следов ошибок БД нет.
- **Отражённый XSS отсутствует.** Проба `GET /search?q=<script>alert(1)</script>` → значение отражено только как `value="&lt;script&gt;alert(1)&lt;/script&gt;"` (экранировано React-атрибутом). Длинная проба (100×`A` + `<img src=x onerror=alert(1)>`) → сырого тега `<img src=x` в ответе нет, только `&lt;img …&gt;` внутри `value`. Ошибка/пустой результат — «Ничего не найдено».
- **Инъекции в путях.** `GET /news/..%2F..%2Fetc%2Fpasswd` → 200 «Не найдено»; `GET /news/<script>…` → штатный 404 без трейса. Несуществующий id → «Не найдено», без 500 и стектрейсов (в ответах нет `SQL`, `stack`, `Traceback`, `Unhandled`).
- **`safeHref` (`lib/url.ts:3-9`) работает.** Allowlist `https?://` + site-relative `/[^/\\]`; `javascript:`, `data:`, `//evil`, `/\` — отклоняются. Применён к партнёрским href (`components/PartnersStrip.tsx:21`), соцсетям (`app/contacts/page.tsx:9-11`), PDF (`components/DocsFilter.tsx:42-43`, `app/page.tsx:37`).
- **Секреты.** `GET /.env.local` → 404. `poweredByHeader: false` (`next.config.js:5`); заголовка `X-Powered-By` у сайта нет (проверено `curl -sI /`). `.gitignore:4-5` покрывает `.env` и `.env.local`. Хардкода паролей в коде нет (`lib/db.ts:3-11` — только `process.env`).
- **API-роутов и мутаций нет.** `route.ts` в `app/` отсутствует; все страницы — серверные SELECT или клиентские фильтры. `ConsultForm` (`components/ConsultForm.tsx:4`) делает только `preventDefault` (см. находку Н3 — это проблема UX, а не утечки).
- **phpMyAdmin закрыт.** `GET http://127.0.0.1:8081/` → 200 с формой логина, `Set-Cookie … HttpOnly; SameSite=Strict`, `X-Frame-Options: DENY`, собственный CSP. Логин не подбирался.
- **Партнёрские ссылки — не реклама.** Информационный характер (логотип + ссылка на ФНПР, правительство края, фонды, вузы), без призывов и вознаграждения — маркировка по ст. 16 закона 38-ФЗ не требуется.

## Находки (по убыванию критичности)

### Н1. HIGH — Next.js 14.2.5 с известными CVE, включая критический обход middleware

- **Место:** `package.json:12` (`"next": "14.2.5"`).
- **Проверка (инспекция):** версия зафиксирована ниже патчей. Публичные бюллетени: CVE-2025-29927 (CVSS 9.1, обход авторизации через заголовок `x-middleware-subrequest`, исправлено в 14.2.25/15.2.3), CVE-2024-46982 (отравление кэша, DoS через `Cache-Control`), CVE-2024-47831 (DoS через Image Optimizer), CVE-2025-49819 (DoS кэша). Сейчас middleware в проекте нет, поэтому CVE-2025-29927 не эксплуатируется напрямую, но любое будущее middleware (админка пресс-службы — в планах, `CONTEXT.md`) унаследует дыру.
- **Фикс:** обновить `next` минимум до 14.2.33 (лучше 15.x), затем `package-lock.json`, `npx tsc --noEmit`, `STATIC_EXPORT=1 npm run build`, регресс-тест экспорта.

### Н2. HIGH — Яндекс.Метрика подключается без проверки согласия из cookie-баннера

- **Место:** `app/layout.tsx:15,27-31` (скрипт `https://mc.yandex.ru/metrika/tag.js` + пиксель `watch/${ym}` при любом заданном `NEXT_PUBLIC_YM_ID`); `components/CookieBanner.tsx:1-27` (флаг `hkoop-cookie` никто не читает).
- **Проверка (инспекция + живой факт):** в `layout.tsx` не ни одного чтения `hkoop-cookie`; условие — только наличие env-переменной. Живой факт: `GET /` сейчас не содержит `mc.yandex`/`metrika` (0 вхождений в сохранённом HTML) — переменной в окружении нет, утечки сегодня нет. Но счётчик «запланирован» (`CONTEXT.md:65`), а `NEXT_PUBLIC_*` запекается в статику при сборке: первая же прод-сборка со счётчиком включит трекинг до клика «Принять», вопреки тексту баннера. Это нарушение ст. 9, 18.1 закона 152-ФЗ и практики Роскомнадзора по cookie.
- **Фикс:** грузить `tag.js` и пиксель только если `lsGet("hkoop-cookie")==="1"` (клиентский компонент-обёртка, по умолчанию выключено); кнопку «Принять» дополнить кнопкой «Отклонить»; смену решения — повторным вызовом баннера из футера.

### Н3. HIGH — Форма консультации имитирует отправку, обращения теряются

- **Место:** `components/ConsultForm.tsx:1-14` (используется на `/` — `app/page.tsx:112` — и на `/contacts` — `app/contacts/page.tsx:28`).
- **Проверка (инспекция):** `onSubmit={(e) => e.preventDefault()}` — данные никуда не уходят, нет `mailto:`, нет fetch, нет состояний success/error, поля не валидируются (`required` нет ни у одного поля, кроме чекбокса). Пользователь жмёт «Отправить» и видит тишину: обращение за бесплатной юридической помощью исчезает. Юридически — введение в заблуждение (ст. 10 закона 2300-1 о достоверной информации об услуге); практически — потеря обращений граждан.
- **Фикс:** либо честная заглушка («Форма скоро заработает, звоните 8 (4212) 32-87-18», кнопку переименовать, данные не собирать), либо `mailto:`/бэкенд с явным сообщением «открылся почтовый клиент / заявка №…». Добавить `required`, `maxLength`, `type="tel"`, статус отправки.

### Н4. MEDIUM — Виджет Яндекс.Карт грузится каждому посетителю до согласия

- **Место:** `app/contacts/page.tsx:23` (`<iframe src="https://yandex.ru/map-widget/v1/?ll=…">`).
- **Проверка (живая):** `GET /contacts` → 200, в теле 2 вхождения `map-widget`; iframe захардкожен, рендерится безусловно. IP, User-Agent и cookie Яндекса уходят до любого клика по баннеру. НПА: та же база, что Н2 (152-ФЗ ст. 9, 18.1).
- **Фикс:** фасад — статичная картинка + кнопка «Загрузить карту»; создавать iframe только после согласия; добавить `referrerpolicy="no-referrer"`; альтернатива — текстовая ссылка «Открыть в Яндекс.Картах».

### Н5. MEDIUM — Нет защитных заголовков; на статике Pages их нечем отдать

- **Место:** весь сайт. Фактические заголовки `GET /`: только `Cache-Control: no-store, must-revalidate`, `Content-Type`, `Vary`. Нет `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
- **Проверка (живая):** `curl -sI /` — перечисленных заголовков нет; в HTML нет `<meta http-equiv>`-компенсаций; сайт можно встроить в чужой iframe (кликджекинг обёртки формы/баннера). Ущерб ограничен (нет авторизации и платежей), поэтому MEDIUM, а не HIGH.
- **Фикс:** для dev/будущего Node-хостинга — `headers()` в `next.config.js` (`frame-ancestors 'self'`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`); для GitHub Pages — `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self' https://mc.yandex.ru; frame-src https://yandex.ru; img-src 'self' data:">` в `layout.tsx` + JS frame-busting на страницах с формой.

### Н6. MEDIUM — `img src` из БД идут мимо `safeHref`: фото книги почёта и логотипы партнёров

- **Место:** `app/honor/page.tsx:14` (`<img src={h.photo}>`), `components/PartnersStrip.tsx:11` (`<img src={p.logo}>`).
- **Проверка (инспекция + данные):** текущие данные безвредны (все фото — `/images/honor/…`, все логотипы — `/images/…`, сверено с `data/*.json`), но поле из БД попадает в `src` без фильтра: запись `https://tracker.evil/p.png` превратит каждую страницу в маяк (IP/UA посетителей третьему лицу без согласия — см. Н2/Н4). Крайний случай: строка `javascript:…` в `src` картинки не исполняется, но ломает рендер; `onError`-вектора в React-пропсах нет, однако сама утечка реальна.
- **Фикс:** `src={safeHref(h.photo) ?? "/images/placeholder.png"}` и то же для `p.logo`; для картинок разрешить только site-relative; добавить `referrerPolicy="no-referrer"` и осмысленный `alt` (сейчас у логотипов `alt=""`, у фото — ФИО, это нормально).

### Н7. MEDIUM — PDF-превью в iframe без `sandbox`, внешний https разрешён

- **Место:** `components/DocsFilter.tsx:42,56` (`preview` из `safeHref(d.file_local)`, `<iframe src={preview} …>` без `sandbox`).
- **Проверка (инспекция):** `safeHref` пропускает любой `https://`-URL, поэтому скомпрометированная строка `file_local` откроет чужой сайт в полноразмерном iframe (фишинг «документа»). Текущие данные — локальные `/docs/*.pdf`, уязвимость спит до порчи данных.
- **Фикс:** `<iframe sandbox="">` (без `allow-scripts`/`allow-same-origin`), для превью разрешить только site-relative `/docs/*.pdf`; внешние URL — только обычной ссылкой с пометкой внешнего ресурса.

### Н8. MEDIUM — Cookie-баннер: нет отказа, ссылка ведёт не на политику, согласие «продолжением»

- **Место:** `components/CookieBanner.tsx:12-25`.
- **Проверка (инспекция + живая):** одна кнопка «Принять», кнопки «Отклонить» нет; ссылка «политикой конфиденциальности» ведёт на `/docs` (каталог), а не на `/docs/politika.pdf` (файл существует — `GET /docs/politika.pdf` → 200, `application/pdf`, ~3,4 МБ); текст «Продолжая, вы соглашаетесь» — implied consent, не явное согласие по ст. 9 152-ФЗ и разъяснениям Роскомнадзора (требуются отдельное действие и возможность отказа; Метрика — аналитическая cookie, а не строго необходимая).
- **Фикс:** две кнопки (Принять/Отклонить), прямая ссылка на `/docs/politika.pdf`, хранение выбора (`hkoop-cookie=1/0`), повторный вызов настроек из футера. НПА: 152-ФЗ ст. 9, 18.1; 149-ФЗ ст. 10.

### Н9. MEDIUM — Чекбокс согласия в форме без ссылки на политику

- **Место:** `components/ConsultForm.tsx:8-10` («Даю согласие на обработку персональных данных», `required`, но без ссылки и без указания оператора).
- **Проверка (инспекция):** рядом нет ни ссылки на `/docs/politika.pdf`, ни наименования оператора, ни целей обработки. Формальное согласие «вслепую» не соответствует ч. 4 ст. 9 152-ФЗ (субъект должен знать оператора, цель, перечень данных).
- **Фикс:** «Даю согласие на обработку персональных данных [Оператором — Союз ХКООП, цель — обратная связь] согласно <a href="/docs/politika.pdf">Политике</a>»; саму политику дополнить разделом о форме.

### Н10. LOW — Книга почёта публикует персональные данные без видимых согласий

- **Место:** `app/honor/page.tsx:11-22`, таблица `honor` (`db/schema.sql:29-36`: `fio`, `photo`, `text` — полные биографии).
- **Проверка (инспекция):** публикуются ФИО + фото + год + биография 7 человек. Фото — биометрические ПД (ст. 11 152-ФЗ, нужно письменное согласие); публикация неограниченному кругу — разрешённые для распространения данные (ст. 10.1, согласие через форму Роскомнадзора). Самих согласий в репозитории нет (и не должно быть — но должен быть регламент).
- **Фикс:** получить/архивировать письменные согласия на публикацию (включая фото) у каждого лица; в `ИНСТРУКЦИЮ-ПРЕСС-СЛУЖБЕ` добавить пункт «без согласия — не публикуем»; по заявлению — снимать карточку в 3-дневный срок.

### Н11. LOW — В импринте нет реквизитов оператора

- **Место:** `components/Footer.tsx:1-31`, `app/contacts/page.tsx:14-24`.
- **Проверка (инспекция):** адрес, телефон, email, часы — есть (ст. 10 149-ФЗ для владельцев сайтов — выполнено). Нет: полного наименования оператора ПДн, ИНН/ОГРН, ответственного за обработку ПДн (требование ст. 22.1 152-ФЗ — назначить ответственного; публикация контактов рекомендована приказом Роскомнадзора).
- **Фикс:** добавить в «Контакты» строку «Оператор персональных данных: Союз ХКООП, ИНН/ОГРН …, ответственный за обработку ПДн: …».

### Н12. LOW — Нет `robots.txt` и `sitemap.xml`

- **Место:** корень сайта. Проверка (живая): `GET /robots.txt` → 404 (штатная страница Next 404, без утечек).
- **Фикс:** добавить `app/robots.ts` и `app/sitemap.ts` (для статического экспорта генерируются автоматически); проверить, что dev-превью закрыто от индексации, а прод — открыт.

## Самопроверка: 5 враждебных сценариев (сделано → сломано → закрыто)

1. **SQL-инъекция в `/news/<id>`.** Ввод `1' OR '1'='1` → связанный параметр, «Не найдено». Не сломано; дополнительно отмечено, что `generateStaticParams` тянет все id без лимита — при росте до тысяч новостей сборка подорожает (рекомендация: `LIMIT` + `dynamicParams`).
2. **XSS через `?q=` и фильтры.** `<script>`, `<img onerror>`, строки 100+ символов → всё экранировано React; сырого HTML в ответе нет. Не сломано.
3. **Траверс `../`, `%2e%2e`, спецсимволы в id.** Параметр уходит в `WHERE id=?`, файловой операции нет → траверс невозможен. Не сломано.
4. **Включение Метрики без согласия.** Сценарий «завтра добавили `NEXT_PUBLIC_YM_ID`» → трекинг до клика (Н2). Сломано при проверке чтением кода → закрыто фиксом Н2.
5. **Отравление БД (злоумышленник с доступом к phpMyAdmin пишет `javascript:`/внешний URL в `partners.url`, `honor.photo`, `documents.file_local`).** `url`/`file_*` режутся `safeHref`, но `photo`/`logo` в `img src` и произвольный https в iframe-превью проходят (Н6, Н7). Сломано → закрыто фиксами Н6/Н7.

## Что уже исправлено ранее — держится

Параметризация SQL, `safeHref`-allowlist для href/iframe, `poweredByHeader: false`, `.env`+`.next-export` в `.gitignore`, отсутствие хардкода пароля, 404 для `.env.local`, phpMyAdmin за логином — всё подтверждено живыми пробами и инспекцией, как новое не засчитывается.

## Вердикт

Показывать людям можно только после Н1–Н3: обновить Next.js, включать Метрику/карту лишь с согласия и починить форму консультации (сейчас обращения теряются); затем — баннер с отказом (Н8), `sandbox`/фильтр картинок (Н6–Н7) и согласия книги почёта (Н10).
