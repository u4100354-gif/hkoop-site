ATTACK 1 [FATAL] Ложное закрытие локализации ПДн без проверки содержания политики и хостинга
Where: раздел «Что уже было исправлено — проверено, держится», абзац «Локализация данных (ч. 5 ст. 18 152-ФЗ) ... Нарушения локализации не установлено»
Problem: задача требует проверить «локализация данных», а для юрвывода нужны два артефакта: содержание `public/docs/politika.pdf` (что там про хранение в РФ / трансграничную передачу) и место хранения/хостинга продакшена. Оппонент не извлёк текст политики (доступность `200` ≠ содержание) и не проверил хостинг статического экспорта на GitHub Pages, но заключает «нарушения не установлено». Контрпример: `curl ... /docs/politika.pdf → 200` доказывает только отдачу байтов; фраза «Яндекс — юрлицо РФ, хранение в РФ» дана без цитаты/источника, а прод по задаче — GitHub Pages (раздача вне РФ) вообще не оценён. Вывод о соответствии ч. 5 ст. 18 и ст. 12 152-ФЗ недоказан и делает итоговый вердикт «можно показывать после H1–H2...» ненадёжным.

ATTACK 2 [FATAL] Фикс M6 не работает там, где живёт прод, — автор сам это доказал выше
Where: «M6. MEDIUM — нет защитных HTTP-заголовков», абзац «Уточняю честно: `headers()` в `next.config.js` при статическом экспорте ... Next игнорирует, а `<meta http-equiv>` не умеет выставлять `X-Frame-Options`, `HSTS` и `frame-ancestors`» против абзаца «Фикс: заголовки настраивать на уровне хостинга ... в самом коде как компенсацию — `<meta http-equiv>` ... плюс JS-защита от встраивания (frame-busting...)»
Problem: прод по задаче — статический экспорт на GitHub Pages (`next.config.js:2,6-7`, `output: "export"`), который кастомных заголовков не отдаёт. Автор сам фиксирует, что `headers()` в прод не эмитится, а meta не закрывает `frame-ancestors`/кликджекинг, но в фиксе снова предлагает `headers()` + meta + `if (top !== self)` frame-busting. Это самопротиворечивый, неприменимый фикс для заявленной площадки: кликджекинг кнопки «Принять»/формы им не закрывается, а «вынести прод за CDN» — смена хостинга без места, шагов и проверки. Пользователь не может действовать без догадок.

ATTACK 3 [MAJOR] Права MySQL выданы за фразу из README, живые гранты не проверены
Where: «M2. MEDIUM — учётка сайта с избыточными правами», место `db/README.md:11 («все права на базу hkoop»)` против `lib/db.ts`
Problem: задача требует проверить «права mysql-пользователя», т.е. живые гранты, а не документацию. `db/README.md:11` — строка «все права на базу hkoop» про желаемую локальную настройку; `lib/db.ts:3-11` показывает только дефолты подключения, а не гранты. Оппонент не приводит `SHOW GRANTS` (read-only, проекту не вредит) и строит факт «при компрометации ... атакующий получит запись/удаление» на допущении «гранты = README». Контрпример: если живой грант уже `SELECT ON hkoop.*`, находка ложна; если `ALL` — это не доказано. Фикс «выполнить read-only `SHOW GRANTS`...» перекладывает невыполненную работу на читателя.

ATTACK 4 [MAJOR] H1 не отвечает на главный вопрос секрета в git и даёт условный фикс
Where: «Допущения» («Статус `db/README.md` в git-истории не проверялся (git трогать запрещено)») + «H1» + «Фикс: ... проверить `git log -- db/README.md`, и если пароль хоть раз был закоммичен — считать скомпрометированным»
Problem: задача запрещает менять проект/БД/git/пакеты/процессы, а не читать их; read-only `git ls-files -- db/README.md`, `git check-ignore`, `git log -- db/README.md` ничего не меняют. Для HIGH-находки «пароли рядом с кодом» обязателен ответ: файл трекается? уже уезжал в историю? Оппонент оставляет оба вопроса открытыми («сформулирована так, чтобы быть верной в обоих случаях») и даёт условный фикс «проверить ... если...». Пользователь не может действовать без догадок: ротировать сейчас или сначала чистить историю.

ATTACK 5 [MAJOR] H2 ранжирован HIGH, хотя живая проба показывает отсутствие передачи данных
Where: «H2. HIGH — Метрика подключается без согласия», проверка «`curl.exe -s http://localhost:3100/ | Select-String "mc.yandex.ru"` в dev-окружении счётчика не находит (переменная не задана), то есть дыра сейчас не стреляет»
Problem: задача — аудит рабочего дерева как есть. По коду `app/layout.tsx:27` вставка за условием `ym && (...)`, где `ym = process.env.NEXT_PUBLIC_YM_ID`; при незаданном ID передачи IP/cookie на `mc.yandex.ru` нет сегодня (собственный probe автора пуст). Ранжировать спящий конфиг как HIGH наравне с активной утечкой паролей (H1) — инфляция severity, ломающая порядок «что чинить первым». Честная схема: текущее состояние — hardening низкого/среднего уровня + отдельный пункт «взведётся при задании YM_ID»; иначе контрпример: деплой без `NEXT_PUBLIC_YM_ID` имеет нулевой трафик к `mc.yandex.ru` при том же HIGH.

ATTACK 6 [MAJOR] В ranked-список положены не-находки: L5 про 404 и L6 с «нарушения не установлено»
Where: «L5. LOW — `/search-index.json` отдаёт 404» («битых ссылок на этот путь в коде не найдено») и «L6. LOW (право) ... Нарушения не установлено»
Problem: задача просит «ranked-список находок» по безопасности и законам РФ. `404` на несуществующий незареференсенный путь — корректное поведение, а не уязвимость и не нарушение НПА; L6 прямо признаёт отсутствие нарушения. Им место в «держится/не требуется», а не в ranked-списке с severity. Дополнительно L5 vague: фикс «или генерировать ... или удалить мёртвое упоминание из документации» при собственном «упоминаний не найдено» — удалять нечего, место упоминания не названо, действовать нельзя.
