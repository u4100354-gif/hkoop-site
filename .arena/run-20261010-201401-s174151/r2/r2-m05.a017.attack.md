ATTACK 1 [MAJOR] Soft-404 из dev выдан за прод-дефект, на статическом экспорте его нет
Where: a006 M5 (строки 98-108): "GET /news/no-such-id-xyz → 200" и фикс "вызывать notFound() ... generateStaticParams + dynamicParams = false"
Problem: Проба снята на dev http://localhost:3100, а прод по задаче — статический экспорт (`next.config.js:6-7` `output: export` при `STATIC_EXPORT=1`) на GitHub Pages (допущение №1 самого отчёта). В `app/news/[id]/page.tsx:11-19` есть `generateStaticParams`, но нет `dynamicParams = false`; в dev неизвестный id рендерит ветку `if (!n)` с кодом 200, а в экспорте такой URL вообще не генерируется и отдаёт хостинговый 404. Контрпример: собрать `STATIC_EXPORT=1 npm run build` и запросить тот же `/news/no-such-id-xyz` на статике — будет 404 хостинга, а не "бесконечное множество URL 200". MEDIUM и вывод про индексацию мусора не доказаны для прода.

ATTACK 2 [MAJOR] Выдуманная поломка IDN в safeHref
Where: a006 L1 (строки 117): "грубое применение нынешнего `safeHref` (только `https?://` и `/[^/\\]`) их может сломать"
Problem: `lib/url.ts:7` — `/^(https?:\/\/|\/[^/\\])/i`, дальше строка возвращается как есть. Контрпример: `safeHref("https://хабаровсккурорт.рф/")` проходит по первой альтернативе `https?://` и возвращается без изменений — кириллический домен не ломается. Поломка возможна только для site-relative кириллицы вида `//...`, которую фильтр и должен резать. Рекомендация "нужен аккуратный хелпер" основана на неверном разборе regex и вводит в заблуждение при фиксе.

ATTACK 3 [MAJOR] Находка P1 без severity нарушает формат задачи
Where: a006 "### P1. Права mysql-пользователя и phpMyAdmin" (строки 149-159) — severity нет; требование задачи: "каждая с severity (CRITICAL / HIGH / MEDIUM / LOW), местом, проверкой и предлагаемым фиксом"
